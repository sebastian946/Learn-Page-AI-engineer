## A system prompt is an API contract

In a demo, the system prompt is a sentence: "You are a helpful assistant." In production, it is the **specification of a component**. It defines inputs, outputs, rules, edge cases and failure behavior. Other code depends on it. If someone edits it casually, downstream parsers, routing logic and evals break — just like changing a public API without a version bump.

So treat it like one:

- It lives in **version control**, as a file, not as a string literal buried in a function.
- It has a **version** and a **changelog**.
- Changes go through **review and automated tests** (evals) before reaching production.
- Every LLM call **logs which prompt version** produced it.

## Anatomy of a contract-style system prompt

A reliable structure, in this order:

1. **Role and goal** – one or two sentences. Who the model is acting as and what success looks like.
2. **Context** – facts about the business that the model cannot guess (policies, product lines, SLAs).
3. **Input description** – what the user message contains and what it never contains.
4. **Output contract** – exact format. With structured outputs the schema enforces shape, but the prompt still explains the *meaning* of each field.
5. **Rules** – explicit MUST / MUST NOT statements, each one testable.
6. **Edge cases and escalation** – what to do when information is missing, the request is out of scope, or the user is abusive.
7. **Examples** – a few short, diverse input → output pairs, including a tricky one.

```markdown
---
id: ticket-triage
version: 1.4.0
owner: support-ai@cartwheel.example
models: [claude-haiku-5-5, claude-sonnet-5-5]
schema: TicketTriage@2
---
You triage customer support tickets for Cartwheel Outfitters, an online
outdoor-gear store shipping to the US and Canada.

## Input
One customer message (email or chat), possibly in English or Spanish.
It may include order ids in the form A-12345. It never includes payment data.

## Output meaning
- category: the single best queue for this ticket (see definitions below).
- priority: urgent only for safety issues, fraud, or orders lost over 10 days.
- confidence: your probability (0-1) that the category is correct.
- summary: one neutral sentence in English, no customer PII.

## Rules
- MUST choose "other" when no category clearly fits. Never invent a category.
- MUST NOT promise refunds, credits or delivery dates.
- MUST NOT copy email addresses or phone numbers into the summary.
- If the message reports a safety hazard (fire, injury), priority is urgent.

## Category definitions
- order_status: customer asks where an order is, with no stated delay.
- shipping_delay: the order is late versus the promised date.
...

## Examples
Input: "Ordered the tent 3 weeks ago, A-10023, still nothing. Ridiculous."
Output: {"category": "shipping_delay", "priority": "high", ...}
```

Notice: every rule can become a test case. "MUST NOT copy email addresses into the summary" becomes an eval that feeds tickets containing emails and asserts the summary has none.

### Writing tips that hold up

- **Be specific, not loud.** "Use urgent only for safety, fraud, or orders lost over 10 days" beats "BE VERY CAREFUL WITH PRIORITY!!!". Modern models follow precise instructions well and over-react to shouting.
- **Explain the why** for non-obvious rules. "Don't promise dates because carrier ETAs are unreliable" helps the model generalize.
- **Define every label.** Overlapping categories (order_status vs shipping_delay) are where accuracy is lost.
- **Keep the system prompt stable.** No timestamps, request ids or user names in it. Put volatile data in the user turn. A stable prefix is also what makes prompt caching effective.
- **Separate instructions from data.** Wrap untrusted content in clear delimiters (for example XML-style tags like `<ticket>...</ticket>`) and tell the model that content inside is data, not instructions. This reduces, but does not eliminate, prompt injection.

## Prompts as files, versions as semver

Store prompts as files with front matter, and load them through a small registry. Semantic versioning maps cleanly:

| Bump | When | Example |
|---|---|---|
| **MAJOR** | Output contract changes in a way consumers must handle | New category added, field renamed, schema version bump |
| **MINOR** | Behavior changes, contract unchanged | Better category definitions, new rule, new examples |
| **PATCH** | No intended behavior change | Typo, formatting, reordering with no effect in evals |

Adding an enum value is **major**: a consumer with an exhaustive `match` on categories will break. This is the same thinking you apply to a REST API.

```python
from dataclasses import dataclass
from hashlib import sha256
from pathlib import Path
import yaml  # pip install pyyaml

@dataclass(frozen=True)
class Prompt:
    id: str
    version: str
    text: str
    meta: dict

    @property
    def fingerprint(self) -> str:
        return sha256(self.text.encode()).hexdigest()[:12]

def load_prompt(prompt_id: str, version: str, root: Path = Path("prompts")) -> Prompt:
    raw = (root / prompt_id / f"{version}.md").read_text(encoding="utf-8")
    _, front, body = raw.split("---", 2)
    meta = yaml.safe_load(front)
    if meta["id"] != prompt_id or meta["version"] != version:
        raise ValueError(f"front matter mismatch in {prompt_id}/{version}")
    return Prompt(prompt_id, version, body.strip(), meta)

# Pin the version in config, never "latest" in production.
TRIAGE = load_prompt("ticket-triage", "1.4.0")
```

Log `prompt_id`, `version` and `fingerprint` with every call. When accuracy drops on Tuesday, you can answer "what changed?" in seconds. The fingerprint catches the classic bug where someone edits a file without bumping the version.

A layout that works:

```text
prompts/
  ticket-triage/
    1.3.0.md
    1.4.0.md
    CHANGELOG.md
tests/
  prompts/
    test_ticket_triage_contract.py   # fast, deterministic checks
evals/
  ticket-triage/
    golden.jsonl                     # labeled examples
```

```markdown
# ticket-triage changelog
## 1.4.0 - 2026-10-28
- Clarified order_status vs shipping_delay using the promised delivery date.
- Eval: macro-F1 0.86 -> 0.89 on golden v3 (n=240). No regressions in urgent recall.
## 1.3.0 - 2026-10-14
- Added rule: never copy emails or phone numbers into summary.
```

## Testing prompts like code

Use your SDET instincts. Build a pyramid:

1. **Static contract tests** (milliseconds, no LLM): front matter is valid, every category in the Pydantic `Literal` is defined in the prompt, examples in the prompt validate against the schema, no forbidden tokens (dates, `{placeholders}` left unrendered).
2. **Eval runs** (minutes, real LLM): run the golden set, compute accuracy per category, compare with the previous version, fail CI if a metric drops beyond a threshold. Module 3 builds this into a GitHub Actions gate.
3. **Online monitoring** (production): repair rate, escalation rate, human override rate per prompt version.

```python
import json, re, typing
from llm_client.prompts import load_prompt
from app.schemas import TicketTriage, Category

def test_every_category_is_defined() -> None:
    prompt = load_prompt("ticket-triage", "1.4.0")
    for cat in typing.get_args(Category):
        assert f"- {cat}:" in prompt.text, f"category {cat} has no definition"

def test_examples_match_schema() -> None:
    prompt = load_prompt("ticket-triage", "1.4.0")
    for line in re.findall(r"^Output: (\{.*\})$", prompt.text, flags=re.M):
        TicketTriage.model_validate({**json.loads(line), "confidence": 0.9, "summary": "x"})
```

Roll out new versions like features: shadow mode (run both, compare), then a percentage rollout behind a flag (module 5), with a one-line rollback to the previous version.

## Common mistakes

- Prompts as inline f-strings scattered across the codebase.
- Editing a prompt in place with no version change, so logs can't explain behavior shifts.
- Shipping "latest" prompts to production instead of pinned versions.
- Rules that cannot be tested ("be smart about priority").
- Volatile data (dates, names) in the system prompt, which defeats caching and makes outputs harder to compare.
- Treating a new enum value as a minor change.

## How this shows up in interviews

<InterviewQuestion question="How do you manage prompt changes in a team?" level="mid">

Prompts are files in the repo with front matter: id, semantic version, owner, target models and the schema version they produce. Changes go through pull requests with a changelog entry. CI runs fast static checks and an eval suite against a golden dataset, and the PR shows the metric diff versus the current version. Production pins an exact version through config, and every call logs prompt id, version and a content hash. New versions roll out in shadow or behind a flag, with instant rollback.

</InterviewQuestion>

<InterviewQuestion question="Why call a system prompt a software contract? What does that change in practice?" level="senior">

Because downstream code depends on its behavior the way it depends on an API: parsers rely on the output format, routing relies on label meanings, analytics rely on consistency. Calling it a contract means it has an explicit spec (inputs, outputs, rules, edge cases), versioning with breaking-change semantics, consumer-driven tests, and change management. In practice: semver where adding a label is major, contract tests that cross-check the prompt with the Pydantic schema, evals as the regression suite, and observability tagged by prompt version, so a quality drop maps to a specific change.

</InterviewQuestion>
