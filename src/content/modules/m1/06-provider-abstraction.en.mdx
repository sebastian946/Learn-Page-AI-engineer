## Why abstract the provider

Most companies hiring AI engineers use more than one model provider. Reasons you will hear:

- **Resilience**: an outage or a rate-limit storm at one vendor should degrade the feature, not kill it.
- **Cost/quality routing**: a cheap model for easy requests, a stronger one for hard ones.
- **Compliance and procurement**: some customers require AWS Bedrock (data stays in their cloud account); others have an existing OpenAI or Anthropic contract.
- **Evaluation**: comparing models on your eval set requires calling them the same way.

The goal is **not** to pretend all models are identical. It is to keep vendor-specific code in one thin layer, so the rest of the system speaks one language: your domain types.

This is the Page Object pattern for LLMs. Tests talk to `LoginPage`, not to selectors. Features talk to `LLMClient`, not to `anthropic.types.ToolUseBlock`.

## The shape of a good abstraction

<Diagram caption="Ports and adapters for LLM providers" chart={`flowchart LR
  F["Features (router, extractor)"] --> C["LLMClient (retries, limits, cost)"]
  C --> P{{"LLMProvider protocol"}}

  P --> O[OpenAIProvider]
  P --> B["BedrockProvider (Converse)"]

Three layers:

1. **Normalized types** – your own `LLMRequest`, `LLMResponse`, `ToolCall`, `Usage`, `StopReason`, `StreamEvent`.
2. **Adapters** – one per provider, translating requests in and responses out, and mapping errors to your own exception hierarchy.
3. **The client** – cross-cutting policies that are provider-independent: retries, rate limiting, concurrency, timeouts, cost logging, fallback between providers.

### Normalized types

```python
from dataclasses import dataclass, field
from enum import StrEnum
from typing import Any, Literal

class StopReason(StrEnum):
    END = "end"
    MAX_TOKENS = "max_tokens"
    TOOL_USE = "tool_use"
    REFUSAL = "refusal"
    OTHER = "other"

@dataclass(frozen=True)
class Usage:
    input_tokens: int
    output_tokens: int
    cache_read_tokens: int = 0
    cache_write_tokens: int = 0

@dataclass(frozen=True)
class ToolCall:
    id: str
    name: str
    arguments: dict[str, Any]

@dataclass
class LLMRequest:
    model: str                           # logical name, e.g. "fast" or "smart"
    messages: list[dict[str, Any]]       # role/content with plain-text content
    system: str | None = None
    max_tokens: int = 1024
    tools: list[dict[str, Any]] = field(default_factory=list)  # name/description/schema
    json_schema: dict[str, Any] | None = None
    temperature: float | None = None     # optional capability, dropped if unsupported
    metadata: dict[str, str] = field(default_factory=dict)  # feature, prompt_version...

@dataclass(frozen=True)
class LLMResponse:
    text: str
    tool_calls: list[ToolCall]
    stop_reason: StopReason
    usage: Usage
    provider: str
    model: str                           # the concrete model id actually used
    latency_ms: float
    raw: Any = None                      # escape hatch for debugging
```

### The protocol and capabilities

```python
from collections.abc import AsyncIterator
from typing import Protocol

@dataclass(frozen=True)
class ModelSpec:
    provider: Literal["anthropic", "openai", "bedrock"]
    model_id: str
    supports_temperature: bool
    supports_json_schema: bool
    max_output_tokens: int

class LLMProvider(Protocol):
    name: str
    async def complete(self, req: LLMRequest, spec: ModelSpec) -> LLMResponse: ...
    def stream(self, req: LLMRequest, spec: ModelSpec) -> AsyncIterator["StreamEvent"]: ...
```

Model ids live in **config**, mapped from logical names. Features ask for `"fast"` or `"smart"`, never for a vendor string. Swapping a model is a config change plus an eval run, not a code change.

```toml
# models.toml — model ids are config. Non-Anthropic ids are examples: check your provider's current list.
[fast]
provider = "anthropic"
model_id = "claude-haiku-5-5"
supports_temperature = false
supports_json_schema = true
max_output_tokens = 8192

[smart]
provider = "anthropic"
model_id = "claude-sonnet-5-5"
supports_temperature = false
supports_json_schema = true
max_output_tokens = 16000

[fast_fallback]
provider = "openai"
model_id = "${OPENAI_FAST_MODEL}"
supports_temperature = true
supports_json_schema = true
max_output_tokens = 8192
```

## Writing an adapter: Anthropic

```python
import time
from anthropic import AsyncAnthropic
import anthropic

_STOP = {"end_turn": StopReason.END, "stop_sequence": StopReason.END,
         "max_tokens": StopReason.MAX_TOKENS, "tool_use": StopReason.TOOL_USE,
         "refusal": StopReason.REFUSAL}

class AnthropicProvider:
    name = "anthropic"

    def __init__(self, client: AsyncAnthropic | None = None) -> None:
        self._client = client or AsyncAnthropic(max_retries=0)  # WE own retries

    async def complete(self, req: LLMRequest, spec: ModelSpec) -> LLMResponse:
        kwargs: dict = {"model": spec.model_id, "max_tokens": req.max_tokens,
                        "messages": req.messages}
        if req.system:
            kwargs["system"] = req.system
        if req.tools:
            kwargs["tools"] = [{"name": t["name"], "description": t["description"],
                                "input_schema": t["schema"]} for t in req.tools]
        if req.json_schema and spec.supports_json_schema:
            kwargs["output_config"] = {"format": {"type": "json_schema",
                                                  "schema": req.json_schema}}
        if req.temperature is not None and spec.supports_temperature:
            kwargs["temperature"] = req.temperature
        start = time.perf_counter()
        try:
            r = await self._client.messages.create(**kwargs)
        except anthropic.RateLimitError as e:
            raise RateLimited(self.name, retry_after=_retry_after(e.response)) from e
        except anthropic.APIStatusError as e:
            raise ProviderError(self.name, e.status_code, retryable=e.status_code >= 500) from e
        except (anthropic.APIConnectionError, anthropic.APITimeoutError) as e:
            raise ProviderError(self.name, None, retryable=True) from e
        return LLMResponse(
            text="".join(b.text for b in r.content if b.type == "text"),
            tool_calls=[ToolCall(b.id, b.name, b.input) for b in r.content if b.type == "tool_use"],
            stop_reason=_STOP.get(r.stop_reason, StopReason.OTHER),
            usage=Usage(r.usage.input_tokens, r.usage.output_tokens,
                        r.usage.cache_read_input_tokens or 0,
                        r.usage.cache_creation_input_tokens or 0),
            provider=self.name, model=r.model,
            latency_ms=(time.perf_counter() - start) * 1000, raw=r,
        )
```

Notice `max_retries=0`. The SDKs retry 429s and 5xx by default (twice for Anthropic). If your client also retries, a single logical call can turn into 9 HTTP calls. Pick **one** layer to own retries. In a multi-provider client, that is your layer, because it can also fail over to another provider.

## The Bedrock adapter in brief

Bedrock's **Converse API** offers one request shape for many model families (Anthropic, Meta, Mistral, Amazon and others). `boto3` is synchronous, so run it in a thread (or use an async AWS client):

```python
import asyncio, boto3
from botocore.exceptions import ClientError

class BedrockProvider:
    name = "bedrock"

    def __init__(self, region: str) -> None:
        self._rt = boto3.client("bedrock-runtime", region_name=region)

    async def complete(self, req: LLMRequest, spec: ModelSpec) -> LLMResponse:
        body = {
            "modelId": spec.model_id,
            "messages": [{"role": m["role"], "content": [{"text": m["content"]}]}
                         for m in req.messages],
            "inferenceConfig": {"maxTokens": req.max_tokens},
        }
        if req.system:
            body["system"] = [{"text": req.system}]
        start = time.perf_counter()
        try:
            r = await asyncio.to_thread(self._rt.converse, **body)
        except ClientError as e:
            code = e.response["Error"]["Code"]
            if code == "ThrottlingException":
                raise RateLimited(self.name, retry_after=None) from e
            raise ProviderError(self.name, None, retryable=code in {"ServiceUnavailableException", "ModelNotReadyException"}) from e
        blocks = r["output"]["message"]["content"]
        return LLMResponse(
            text="".join(b.get("text", "") for b in blocks),
            tool_calls=[ToolCall(b["toolUse"]["toolUseId"], b["toolUse"]["name"], b["toolUse"]["input"])
                        for b in blocks if "toolUse" in b],
            stop_reason=_STOP.get(r["stopReason"], StopReason.OTHER),
            usage=Usage(r["usage"]["inputTokens"], r["usage"]["outputTokens"]),
            provider=self.name, model=spec.model_id,
            latency_ms=(time.perf_counter() - start) * 1000, raw=r,
        )
```

For Claude specifically on Bedrock, the Anthropic SDK also ships a dedicated Bedrock client with the same `messages.create` surface. Converse is the right choice when you want one adapter for several model families.

## Normalize errors, not just responses

Your retry and fallback logic must not import vendor exceptions. Map everything to a small hierarchy:

```python
class LLMError(Exception):
    def __init__(self, provider: str, status: int | None = None, retryable: bool = False):
        super().__init__(f"{provider} error status={status}")
        self.provider, self.status, self.retryable = provider, status, retryable

class RateLimited(LLMError):
    def __init__(self, provider: str, retry_after: float | None):
        super().__init__(provider, 429, retryable=True)
        self.retry_after = retry_after

class ProviderError(LLMError): ...
```

`400` (bad request) and `401/403` (auth) are **not** retryable: retrying wastes time and hides bugs. `429`, `5xx`, Anthropic's `529 overloaded`, timeouts and connection errors are retryable.

## Build vs. buy

Libraries like LiteLLM or LangChain's chat model interfaces already normalize dozens of providers. Using one is reasonable. Building a thin layer yourself (as in the exercise) is still worth it because:

- you control retries, cost logging and error semantics exactly;
- you understand what the library does when it misbehaves;
- interviewers ask you to design this.

A good compromise in real projects: a thin internal interface (`LLMClient`) whose adapters may wrap a library.

## Common mistakes

- **Lowest-common-denominator design** that hides useful features (prompt caching, structured outputs). Add capability flags and an escape hatch (`provider_options`) instead.
- **Vendor types leaking** into features, so a switch requires touching 40 files.
- **Retrying in two layers** (SDK and yours).
- **Model ids hard-coded** in feature code instead of config.
- **No fake provider**, so unit tests hit real APIs, cost money and flake.
- **Assuming identical behavior.** The same prompt can perform very differently across models. Each model in the fallback chain needs its own eval run.

## How this shows up in interviews

<InterviewQuestion question="Design an LLM client that can switch between Anthropic, OpenAI and Bedrock." level="senior">

Ports and adapters. A protocol with `complete` and `stream` that takes my normalized request and returns a normalized response: text, tool calls, normalized stop reason, usage, concrete model id, latency. One adapter per provider maps requests, responses and errors into my types, with a capability spec per model (JSON schema support, temperature, max output) loaded from config with logical names like fast and smart. Cross-cutting policy lives above the adapters: retries with jittered backoff (SDK retries disabled), rate limiting, concurrency caps, timeouts, provider fallback, and cost logging tagged by feature and prompt version. A fake provider supports unit tests, and every model in the fallback chain is validated on the same eval set because prompts don't transfer perfectly.

</InterviewQuestion>
