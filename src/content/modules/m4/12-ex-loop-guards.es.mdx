## Objetivo

En el ejercicio 08 construiste `langgraph-hitl-agent`: un agente LangGraph con una compuerta de aprobación antes de las herramientas riesgosas. Ahora mismo nada le impide entrar en bucle para siempre o gastar sin límite. En este ejercicio agregas tres guardas y pruebas cada una con un test determinista:

1. **Máximo de pasos** — el agente se detiene después de `MAX_STEPS` llamadas al modelo.
2. **Detección de acciones repetidas** — el agente se detiene cuando la misma tool call (nombre más argumentos) aparece `REPEAT_THRESHOLD` veces.
3. **Presupuesto de costo por ejecución** — el agente se detiene antes de una llamada al modelo que empujaría la ejecución por encima de `MAX_COST_USD`.

Cada parada debe ser elegante: un mensaje final claro, un `stop_reason` en el estado y un ticket para un humano. Ninguna excepción debe llegar a quien invoca.

Tiempo: 60 minutos. No vas a llamar a un modelo real. Los tests usan un modelo de chat falso que entra en bucle a propósito, igual que harías un stub de una dependencia flaky en un test de integración.

## Contexto

Piensa en esto como agregar timeouts y circuit breakers a un servicio que ya es tuyo. Las guardas viven en el grafo, no en el prompt. Un prompt que dice "no te repitas" es una sugerencia. Un router que revisa un contador es un contrato.

Los precios vienen de `config/pricing.yaml`. Usa valores de ejemplo y etiquétalos como ejemplos. Los tests deben inyectar sus propios precios para no depender nunca de precios reales.

<AcceptanceCriteria>

- [ ] `AgentState` tiene `step_count: int`, `cost_usd: float` y `stop_reason: str | None`, con valores por defecto razonables en la entrada del grafo.
- [ ] El nodo del agente incrementa `step_count` y suma el costo de cada respuesta calculado con `usage_metadata` y un dict de precios.
- [ ] Un router de guardas corre después del nodo del agente y antes de las herramientas. Enruta a `stop` por máximo de pasos, acción repetida o presupuesto, a `tools` si hay tool calls, y a `END` en otro caso.
- [ ] La revisión de presupuesto usa una estimación previa, así que una llamada que excedería el presupuesto nunca se hace.
- [ ] El nodo `stop` escribe un `AIMessage` para el usuario, define `stop_reason` como `max_steps`, `repeated_action` o `budget`, y llama `create_ticket` con el thread id.
- [ ] `recursion_limit` sigue definido en la config de invoke como respaldo, mayor que `MAX_STEPS * 2 + 5`.
- [ ] Los límites se leen de env o config (`MAX_STEPS`, `REPEAT_THRESHOLD`, `MAX_COST_USD`) con valores por defecto.
- [ ] Tres tests de pytest, uno por guarda, con un modelo falso. Sin red. Tiempo total de tests por debajo de 2 segundos.
- [ ] Un test prueba que una ejecución normal (dos tool calls y luego una respuesta final) no se ve afectada por las guardas.
- [ ] El README tiene una sección "Guards" con los límites, cómo se eligieron y los valores de `stop_reason`.

def call_signature(name: str, args: dict) -> str:

from hitl_agent.graph import build_graph
from tests.fakes import ScriptedModel  # from exercise 08
from langchain_core.messages import AIMessage

def looping_model(n: int = 50) -> ScriptedModel:
    msgs = [AIMessage(content="", tool_calls=[{
        "name": "get_order", "args": {"order_id": "ORD-1001"}, "id": f"call_{i}"}],
        usage_metadata={"input_tokens": 1200, "output_tokens": 40, "total_tokens": 1240})
        for i in range(n)]
    return ScriptedModel(msgs)

def test_repeated_action_stops_run(fake_backend):
    graph = build_graph(looping_model(), MemorySaver(), backend=fake_backend)
    out = graph.invoke({"messages": [("user", "Where is ORD-1001?")]},
                       config={"configurable": {"thread_id": "t-repeat"}, "recursion_limit": 40})
