## Company context

Tidewater Freight is a fictional mid-size third-party logistics company. It runs four warehouses in the US Midwest and East Coast and ships about 18,000 orders a day for 140 e-commerce brands. It does not own trucks. It books parcel and LTL capacity with six carriers and resells it to its clients.

The customer operations team has 22 agents. They work a shared inbox and a ticketing system. Most of their day is repetitive: "Where is my order?", "Can you deliver on Friday instead?", "The box arrived damaged", "Please cancel this order before it ships", "What would it cost to ship this pallet to Denver?". Each request needs two to five lookups across the order management system (OMS), carrier APIs and the ticketing tool.

Average handling time is 9 minutes per email. Peak season doubles the volume. Last November the backlog reached 3 days and two large clients threatened to leave. Leadership wants an agent that handles the routine work end to end and prepares the risky work for a human to approve in one click.

## Business goal

Automate the five most common request types so that at least 60% of inbound operations emails are resolved without a human touching them, and the rest arrive in the queue already researched, with a proposed action and a one-click approval. Every action must be logged and explainable to Finance and to the client.

## Functional requirements

1. **Intake.** Read new emails from a mailbox fixture (JSON or `.eml` files) and new order events from a queue fixture. Extract intent, order ids and customer id. Ignore auto-replies and newsletters.
2. **Tools.** Implement and expose these tools with typed schemas and the standard error contract (`code`, `message`, `retryable`, `hint`):
   - `get_order(order_id)` and `list_orders(customer_id, status, cursor, limit)` (paginated)
   - `get_carrier_rates(origin_zip, dest_zip, weight_kg)`
   - `reschedule_delivery(order_id, new_date, idempotency_key)`
   - `create_ticket(order_id, category, summary)`
   - `issue_refund(order_id, amount_cents, reason, idempotency_key)`
   - `cancel_order(order_id, reason, idempotency_key)`
3. **Agent.** A LangGraph `StateGraph` with typed state, a tools node, conditional routing and a Postgres or SQLite checkpointer so runs survive restarts.
4. **Human-in-the-loop.** `issue_refund` and `cancel_order` always pause with `interrupt()` and show the approver the proposed call, the order details and the agent's reasoning summary. The approver can approve, reject or edit the arguments (for example lower the refund amount). The run resumes with `Command(resume=...)`. Refunds over 500 USD also require a reason code.
5. **Reply drafting.** For resolved requests, the agent drafts a customer reply grounded in tool results. In this capstone, replies are written to an outbox folder, not sent.
6. **Step logging.** Every node execution and tool call emits one structured JSON log line: `run_id`, `thread_id`, `step`, `node`, `tool`, `args` (PII-masked), `result_code`, `latency_ms`, `input_tokens`, `output_tokens`, `cost_usd`. Traces go to LangSmith or Langfuse.
7. **Guards.** Max steps per run, repeated-action detection, per-run cost cap and a per-client daily budget. Every stop sets `stop_reason` and opens a ticket for a human.
8. **Trajectory eval suite.** At least 30 scenarios, run in CI, covering every intent, HITL approve/reject/edit, tool failures, missing data and prompt injection in email bodies.
9. **Optional.** Serve the order and carrier tools from an MCP server, reusing your `mcp-servers-lab` work, and have the agent load them through an MCP client adapter.

| Accuracy | Final-state pass rate at least 95% on the eval suite. Trajectory match rate at least 85%. Zero forbidden tool calls (refund or cancel without approval). |
| Reliability | Transient tool errors retried in code. A carrier outage degrades to "rates unavailable" plus ticket, never a crash. |
| Auditability | Every refund and cancellation has an approver id, timestamp, original and edited arguments in an audit table. |
| Security | PII (emails, phone numbers, addresses) masked in logs. Tools run with a least-privilege service account. Email bodies are treated as untrusted data. |

## Out of scope

- Sending real emails or integrating a real mailbox. Use fixtures.
- Real carrier or OMS integrations. Use fake services with realistic data and latency.
- A production approval UI. A CLI or a minimal FastAPI endpoint is enough.
- Multi-language support. English only.
- Deploying to AWS. That is module 5.

- Running `make demo` processes the 20 fixture emails, writes replies to `outbox/`, queues risky actions and prints a summary table.
- Approving, rejecting and editing a queued refund each work from the CLI and are recorded in the audit table.
- Restarting the process mid-approval and then approving resumes the same thread without repeating earlier tool calls.
- Every run produces JSON log lines and a trace link. No raw email address or phone number appears in logs.
- Guards are covered by tests with a fake looping model.
- CI runs unit tests on every push and the trajectory suite on PRs, and blocks merge below the accuracy targets above.

Key design choices to justify in your README:

- **One agent, not a multi-agent system.** Five intents and seven tools fit one well-prompted agent. Explain why a supervisor would add latency and cost without benefit here (lesson 10).
- **Deterministic intake.** Parsing order ids with a regex and a small classifier is cheaper and more testable than letting the agent discover them.
- **Approval as a graph node.** HITL lives in the graph, not in the tool, so the decision is checkpointed and auditable.
- **Fake backends as first-class code.** The same fakes power unit tests, evals and the demo.

## How to present this in an interview

Use a 4-minute structure. Interviewers remember stories with numbers.

**1. The problem (30 seconds).** "A 3PL with 22 ops agents, 9 minutes per email, a 3-day backlog in peak. The goal was to automate routine requests end to end and make risky ones one-click approvals."

**2. The architecture (60 seconds).** Show the diagram. Say why it is one agent and not five: "Seven tools and five intents fit one agent. A supervisor would add a model call per request and another place to fail." Point to the approval node: "Refunds pause inside the graph with `interrupt()`. The state is checkpointed in Postgres, so an approval can come hours later, after a deploy, and the run resumes exactly where it stopped."

**3. Safety and cost (60 seconds).** "I treated the agent like an untrusted service. Writes need idempotency keys. Refunds and cancellations cannot execute without a human. Guards stop loops on step count, repeated calls and cost. Every stop has a reason and opens a ticket." Give your measured numbers: cost per 1,000 requests, p95 latency, guard trip rate.

**4. Evals, the SDET angle (60 seconds).** "Output-only checks miss the dangerous bugs, like the agent saying it opened a ticket when it didn't. My suite runs 30+ scenarios three times each against a fake backend and asserts on recorded writes. It checks trajectories with the loosest match mode that still catches the bug, and fails CI on any forbidden call." Mention one regression the suite caught during development.

**5. Trade-offs and next steps (30 seconds).** What you would change for production: real mailbox integration, an approval UI, online evaluation on sampled traces, per-client prompt variants behind feature flags, deploy on ECS (module 5).

Prepare for follow-ups:

- "What happens if the approver edits the refund to an invalid amount?" (Validation in the tool, error contract, the agent explains and re-queues.)
- "How do you stop a malicious email from triggering a refund?" (Untrusted input, refunds gated by humans, injection scenarios in evals, least-privilege tools.)
- "How did you pick the step limit?" (p95 of successful traces plus headroom.)
- "Why not just a workflow?" (Intake and approvals are workflow-like and deterministic; only the research and resolution step is agentic. Show where you drew the line.)
