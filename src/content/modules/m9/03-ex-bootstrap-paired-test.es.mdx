## Objetivo

Tu equipo tiene dos prompts para el router de tickets de soporte del módulo 1: `v1` (en producción) y `v2` (una reescritura con definiciones de categorías más claras). Alguien corrió ambos una vez y publicó en Slack "¡v2 es 3 puntos mejor!". Tu trabajo es producir una respuesta que sobreviva a un staff engineer escéptico:

1. Corre ambos prompts sobre **los mismos** tickets etiquetados, 3 veces cada uno, con caché.
2. Mide el piso de ruido A/A (v1 vs v1).
3. Reporta accuracy y macro-F1 de cada prompt con intervalos de confianza bootstrap al 95%.
4. Reporta la diferencia **pareada** con un CI, una prueba exacta de McNemar y una prueba de permutación pareada.
5. Estima cuántos ítems necesitarías para detectar una diferencia de 3 puntos con 80% de potencia.
6. Escribe un `REPORT.md` de una página que termine con una recomendación clara.

Esta es la primera carpeta de un nuevo repo, `llm-eval-lab`, que reúne todos los ejercicios del módulo 9.

## Contexto

Usa al menos 200 tickets etiquetados. Reutiliza el dataset de `support-ticket-router` si lo tienes. Si no, genera un set semilla con un LLM y luego **vuelve a etiquetar cada ítem tú mismo** para que las etiquetas gold sean humanas. Mantén al menos 5 categorías y asegúrate de que una categoría sea rara (5–8% de los ítems), por ejemplo `legal_threat`. Las clases raras son donde macro-F1 y accuracy no coinciden.

Formato de fila para `data/tickets.jsonl`:

```json
{"id": "t-0042", "text": "I was charged twice for order 88123 and want my money back today.", "label": "billing_refund"}
```

Formato del caché de predicciones para `runs/<prompt>-run<k>.jsonl`:

```json
{"id": "t-0042", "pred": "billing_refund", "latency_ms": 812, "input_tokens": 412, "output_tokens": 9}
```

<Hints>
  <Hint>Separa la generación del análisis. `run_prompts.py` es el único archivo que llama a la API. `analyze.py` solo lee archivos en caché, así que puedes iterar sobre la estadística gratis. Usa el SHA-256 del archivo de prompt en la llave del caché para que editar `v2.md` invalide sus corridas automáticamente.</Hint>
  <Hint>Macro-F1 no es un promedio de puntajes por ítem, así que no puedes hacer bootstrap de un vector de números por ítem. Remuestrea índices y recalcula la métrica completa en cada remuestreo, para ambos prompts sobre los mismos índices. Eso es lo que la hace pareada.</Hint>
  <Hint>Para McNemar, construye vectores booleanos `correct_a = pred_a == gold` y `correct_b = pred_b == gold`. `a_only = (correct_a & ~correct_b).sum()`. La tasa de discordancia para la fórmula de tamaño de muestra es `(a_only + b_only) / n`. Si tu prueba A/A ya muestra 5% de discordancia, tus ítems son ruidosos y el voto mayoritario entre corridas importa.</Hint>
  <Hint>Una buena estructura de reporte: una tabla con accuracy y macro-F1 por prompt y sus CIs; una tabla con las diferencias pareadas, CIs y p-values; una línea con el piso A/A; una línea con el n requerido; luego la recomendación. Si el CI de la diferencia incluye 0, la respuesta honesta es "no hay evidencia de que v2 sea mejor con n = 200; necesitamos unos N ítems", no "v2 es un poco mejor".</Hint>
