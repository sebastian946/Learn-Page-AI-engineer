## The distribution is the answer

A Choice or Score answer is not the top option. It is the whole `probabilities` map, and `choice` or `score` is a summary of it. `confidence` is a second summary: a single number from 0 to 1 that describes how **peaked** the distribution is. It is 1 when all the probability is on one outcome and 0 when it is spread evenly.

Read that definition twice, because the most common mistake in this module hides inside it. **Confidence is a statistic of the shape of the distribution. It is not the probability that the answer is correct.** A model can put 100% on `billing` for a technical ticket. Its confidence is 1.0 and it is wrong. Whether high confidence tends to go with correct answers is an empirical property called calibration, and you measure it on your own labeled data (lesson 09 and 10). TypeSafe trains for it and makes no guarantee about it.

## The three formulas

TypeSafe publishes the exact formulas, so you can recompute `confidence` from `probabilities` and, when it suits you, replace it with a different statistic.

**Noul.** There is no `confidence` field. The value `p` already carries the uncertainty: near 0.5 means unsure. If you want a confidence-style number on the same scale as a Choice, use the distance from the midpoint:

`confidence = |2p − 1|`

**Choice** with `n` options, where `p_max` is the probability of the selected option:

`confidence = (p_max − 1/n) / (1 − 1/n)`

That is "how far above an even split is the winner", rescaled so an even split is 0 and certainty is 1. Only the top probability counts: `(0.6, 0.3, 0.1)` and `(0.6, 0.2, 0.2)` both give 0.4.

**Score** with `n` ordered levels, `m` the most likely level and `p_i` the probability of level `i`:

`confidence = max(0, 1 − Σ p_i·|i − m| / MAD_unif)` where `MAD_unif = (1/n) Σ |i − (n−1)/2|`

The numerator is the average distance, in levels, from the peak. The denominator is that same distance for an even spread. Probability on a neighbouring level costs less confidence than probability far away: with three levels, `(0, 0.5, 0.5)` gives 0.25 and `(0.5, 0, 0.5)` gives 0.

```python
def noul_confidence(p: float) -> float:
    return abs(2 * p - 1)


def choice_confidence(probabilities: dict[str, float]) -> float:
    n = len(probabilities)
    return (max(probabilities.values()) - 1 / n) / (1 - 1 / n)


def score_confidence(probabilities: dict[int, float]) -> float:
    levels = sorted(probabilities)
    n = len(levels)
    m = max(levels, key=lambda i: probabilities[i])
    spread = sum(probabilities[i] * abs(i - m) for i in levels)
    even_spread = sum(abs(i - (n - 1) / 2) for i in levels) / n
    return max(0.0, 1 - spread / even_spread)


assert round(choice_confidence({"a": 0.61, "b": 0.35, "c": 0.04}), 2) == 0.42
assert round(score_confidence({0: 0.0, 1: 0.57, 2: 0.43}), 2) == 0.35
```

Those two asserts reproduce the numbers in lesson 02's response examples. Keep this file in `jev-lab`; it is a unit test of your understanding and of the API's contract.

## Why 0.5 means different things

A top probability of 0.5 is a coin flip between two options and a strong signal among ten. The Choice formula absorbs that: `p_max = 0.5` gives confidence 0 with `n = 2` and 0.44 with `n = 10`. That is the point of the rescaling, and it is why a single confidence threshold can be reused across questions with different option counts. It is also why you must not compare raw `p_max` across questions without thinking about `n`.

Two alternative statistics the docs suggest, both computed from the same map:

- **Top probability** `p_max`: reads directly as "how likely is the chosen option". Set its threshold per question, because of the `n` effect.
- **Top-to-second ratio** `p_max / p_second`: how clearly the winner beats the runner-up, ignoring the tail. Good for routing where only the top two matter.

Try them side by side on your labeled set; keep whichever separates right from wrong answers best.

## Three bands, scaled by risk

The pattern the docs recommend, and the one you will build in the next exercise, splits confidence into three ranges:

| Band | System behaviour | Example |
|---|---|---|
| High | Act automatically | Assign the ticket, show the balance |
| Medium | Act with a safeguard | Ask the user to confirm, flag for review, gather more state |
| Low | Do not act | Human queue, clarification, fallback to an LLM |

The boundaries are not one number. **They scale with the cost of being wrong**, per action, inside the same system:

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Gate:
    act: float      # confidence at or above this: act automatically
    confirm: float  # between confirm and act: safeguard; below confirm: human


GATES = {
    "show_balance": Gate(act=0.5, confirm=0.3),        # wrong screen is recoverable
    "assign_team": Gate(act=0.7, confirm=0.4),         # misroute costs minutes
    "approve_transfer": Gate(act=0.95, confirm=0.6),   # wrong approval costs money
}


def band(action: str, confidence: float) -> str:
    g = GATES[action]
    if confidence >= g.act:
        return "auto"
    if confidence >= g.confirm:
        return "confirm"
    return "human"
```

For Nouls the same shape appears as two thresholds on `p`: yes above 0.7, no below 0.3, the middle to a person. Raise the yes threshold when acting on a false yes is expensive (paging, refunds). Lower it when missing a true yes is expensive (safety flags).

<Callout type="tip" title="SDET lens: a threshold is a test-strategy decision">

You already decide which checks block a merge, which only warn, and which page someone at 3 a.m. Confidence gating is the same decision. "Auto" is a blocking assertion. "Confirm" is a warning with a human in the loop. "Human" is "we do not trust the oracle here". Write the thresholds down with the reason, like you would a flaky-test policy.

</Callout>

## Validating thresholds on your own data

A threshold you picked from three examples in the Playground is a guess. Validate it the way Module 9 validated an LLM judge: on a labeled set, with intervals.

1. Label 200–500 items with the true answer. Reuse Module 1 or Module 9 tickets.
2. Run every item through Jev once. Store `choice`, `probabilities`, `confidence`, `model`.
3. For each candidate threshold `t`, compute **coverage** (fraction with confidence at or above `t`) and **precision among covered** (fraction of those that are correct).
4. Plot precision against coverage. The curve tells you what accuracy you buy at each level of automation. Pick the threshold that meets the accuracy target for that action, then read the coverage off the curve to estimate the human workload.
5. Put a bootstrap interval on the precision at the chosen threshold (Module 9, lesson 02). With 300 items and 60% coverage you have 180 covered items; the interval is wide, and you should say so.

```python
import numpy as np


def precision_coverage(conf: np.ndarray, correct: np.ndarray, thresholds: np.ndarray):
    rows = []
    for t in thresholds:
        covered = conf >= t
        n = int(covered.sum())
        precision = float(correct[covered].mean()) if n else float("nan")
        rows.append({"t": float(t), "coverage": n / len(conf), "precision": precision, "n": n})
    return rows
```

If the curve is flat, confidence carries no information for this question on this data. That happens: the question may be badly posed, or the levels may overlap. Rewrite the question before you tune the number.

## Common mistakes

- **Reading confidence as accuracy.** Say "the distribution is peaked", not "the model is 90% sure it is right".
- **One global threshold.** Use one per action, scaled by the cost of a wrong action.
- **Comparing `p_max` across questions with different `n`.** Use `confidence` or per-question thresholds.
- **Tuning on the same ten examples you tested on.** Hold out, or at least bootstrap.
- **Tuning on `jev-latest`, then letting the alias move.** Record the versioned `model` next to every threshold.

## How this shows up in interviews

<InterviewQuestion question="Jev returned confidence 0.9 for a Choice. What can you conclude, and what can't you?" level="senior">

I can conclude that the probability distribution over the options is strongly peaked: with the published formula, the top option sits far above an even split. For three options that means `p_max` is about 0.93. I cannot conclude that the chosen option is correct. Confidence is a property of the output distribution, not an error rate. Whether confidence 0.9 corresponds to roughly 90% precision is calibration, which I measure on labeled data with a reliability curve, and it can differ by question, by domain, and by model version. So my answer in a design review is: gate on it, but publish the precision-at-threshold number from our own data next to the threshold, with a confidence interval.

</InterviewQuestion>
