## Company context

Kestrel Market is a fictional peer-to-peer marketplace for refurbished electronics. About 40,000 listings go live each week, 9,000 support conversations start each day, and a seller-facing assistant ("Kestrel Helper") answers policy and listing questions from a help-center corpus. The operations team of 22 people reviews listings, routes tickets, and audits the assistant's answers.

Today every automated decision in that flow is an LLM call with a JSON schema: listing moderation (is this listing prohibited, miscategorised, suspicious?), ticket triage (department, urgency, tone), the Helper's input and output guardrails, and the help-center re-ranker. It works, but each call takes 1.5–4 seconds, the monthly model bill is the second-largest line in the ops budget, and the schema-only outputs give the team no probability to decide what to automate. Everything either auto-runs or goes to a human by static rule.

Leadership has read about System One models and wants a **real-time decision layer**: Jev for every snap judgment, the LLM kept for anything a person reads, and a human queue fed by confidence rather than by fixed rules. They want it measured against the current pure-LLM baseline before anyone changes production.

## Business goal

Cut the cost and latency of automated marketplace decisions by replacing LLM calls with Jev where a typed snap judgment is enough, **without** lowering accuracy on the decisions that matter, and introduce confidence-gated automation so the ops team reviews the uncertain cases instead of a fixed share of everything. Produce the evidence that lets Amara and Yusuf decide whether to roll it out.

## Functional requirements

1. **Decision service.** A FastAPI service exposing four decision points, each one Jev request built with speculative fan-out: `POST /decide/listing` (prohibited Noul, category Choice over the marketplace taxonomy with at least 30 options, suspicious-pricing Noul, condition Score), `POST /decide/ticket` (department Choice over 8 teams, urgency Noul, frustration Score, wants-human Noul, language Choice), `POST /guardrail/input` and `POST /guardrail/output` (the hazard battery: injection, safeguard-drop, harm request, off-topic, PII-in-output, plus a harm Score), `POST /rerank` (one Noul per (query, passage) over up to 30 help-center passages, concurrent).
2. **Confidence-gated routing.** Every decision returns a band (`auto`, `confirm`, `human`) per action using thresholds from a versioned `thresholds.yaml`, chosen per action by the cost of a wrong action and validated on labeled data with the precision/coverage method from exercise 05.
3. **Human queue.** Decisions in `confirm` and `human` bands land in a queue table with the full answers map; a minimal reviewer endpoint records the human label. Human labels feed the next calibration run.
4. **LLM fallback on the same schema.** For each decision point, an adapter that answers the identical questions with a Claude structured-output schema (model id from config). Used when Jev times out or fails after retries, flagged in logs, gated with stricter thresholds. Guardrails fail closed; re-ranking fails open to BM25 order.
5. **Labeled datasets.** At least 300 labeled listings, 300 labeled tickets, 200 labeled guardrail messages (including at least 60 adversarial ones reused from Module 3), and 40 help-center queries with gold passages. Label yourself; document the guideline.
6. **Calibration eval suite.** For every Noul and the top probability of every Choice: accuracy or F1, reliability table, Brier, ECE (equal-mass bins), bootstrap intervals, and a regression test with a committed baseline per pinned model version (exercise 10 generalised).
7. **Baseline comparison.** Run the pure-LLM adapters on the same datasets and report, paired: quality, calibration, p50/p95 latency and cost per 1,000 decisions, with provider prices read from config and dated.
8. **Cost/latency dashboard.** A small page or notebook export that shows, per decision point: automation rate (share in `auto`), human-queue rate, p50/p95, cost per 1,000 for Jev versus baseline, fallback rate, and the pinned model id.
9. **Observability.** Every decision logged with request id, decision point, versioned model, answers map, band, thresholds version, source (`jev` or `llm_adapter`), latency and input tokens; state logged as a hash only.

## Non-functional requirements

| Requirement | Target |
|---|---|

| Latency, re-rank over 30 passages | p95 under 1.2 s with concurrent fan-out |
| Accuracy, ticket department | Macro-F1 not lower than the LLM baseline by more than 2 points (paired bootstrap, lower bound) |
| Precision among `auto` decisions | At least 0.95 for listing moderation and guardrails, 0.90 for triage, on held-out labels |
| Guardrail recall for adversarial messages | At least 0.95 at the production threshold; failures fail closed |
| Calibration | ECE (equal-mass, 10 bins) under 0.08 on every gated Noul; reported with intervals |
| Cost | Cost per 1,000 decisions for Jev decision points at least 10x below the LLM baseline, prices dated |
| Resilience | Jev outage simulated in tests: guardrails hold, re-rank falls back, triage uses the adapter, alert fires |
| Versioning | Versioned Jev id pinned in config; alias used only in a documented "canary" job |
| Privacy | PII masked before the state is built; no raw state in logs; DPA checklist in the README |

## Out of scope

- Replacing the LLM that writes replies or answers help-center questions.
- A production-grade reviewer UI; a JSON endpoint and a table are enough.
- Fine-tuning any model. Jev is shaped only through state, instructions and criteria.
- Multimodal moderation of listing photos.
- Deploying to the cloud; Docker Compose locally with the Module 5 patterns is the target.

## Acceptance criteria

- The four decision points work end to end against recorded responses in tests and against live Jev (or a gateway) when a key is present.
- Every threshold in `thresholds.yaml` traces to a row in `THRESHOLDS.md` with data behind it.
- The calibration regression test runs in CI and fails on a degraded baseline.
- The eval report compares Jev and the LLM baseline on the same items with paired intervals and dated prices.
- Outage tests prove fail-closed guardrails, fail-open re-ranking and the adapter fallback for triage.
- The dashboard shows automation rate, queue rate, latency, cost and fallback rate per decision point.
- No raw customer text appears in logs or in the repo.

## How to present this in an interview

Open with the one-sentence framing: "I replaced the snap-judgment LLM calls in a marketplace ops flow with a System One model and added confidence-gated automation, measured against the LLM baseline." Then show the dashboard: automation rate, queue rate, cost per 1,000 and p95 per decision point, Jev next to baseline.

Expect four questions. **"How do you know the probabilities mean anything?"** Show the reliability curve and the ECE with intervals, explain equal-mass bins, and say what you did when a Noul was badly calibrated. **"What happens when the vendor is down?"** Walk the degradation table: fail closed, fail open, adapter, alert. **"Why not just use the LLM with a schema?"** Give the paired numbers, then be honest about where the LLM still wins: it can explain, and it handles the multi-hop and arithmetic cases Jev's own docs say it cannot. **"How did you pick the thresholds?"** Precision/coverage sweep, lower bound of the interval, per action by cost of a wrong action, pinned model id, regression test.

Close with the SDET angle: each Jev question is an oracle you can run on every request, so the eval suite and the production path are the same code, and the human queue is the labeling pipeline. That is the part most candidates cannot say.
