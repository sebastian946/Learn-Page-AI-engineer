## Why rebuild what already works?

In lesson 01 you built a RAG pipeline in about 30 lines of LangChain. It worked. So why spend a lesson rebuilding it with plain libraries?

Because frameworks hide decisions, and interviews, outages and cost reviews are all about those decisions. When a senior engineer asks "what SQL does your retriever run?" or "what happens when the embedding API returns a 429 halfway through ingestion?", "LangChain handles it" is not an answer.

It is the same reason you once wrote a raw HTTP test before trusting a Playwright helper: you need to know what the abstraction does so you can debug it when it leaks.

The goal is not to abandon frameworks. LangChain and LangGraph are fine choices in production. The goal is to be able to choose, and to drop down a level when you need to.

## What LangChain was doing for you

Here is the lesson 01 pipeline, mapped to what each abstraction hides.

| LangChain piece | What it actually does | Decisions it made for you |
|---|---|---|
| `Document` | A dict with `page_content` and `metadata` | Metadata schema (none enforced) |
| `RecursiveCharacterTextSplitter` | Splits on `\n\n`, `\n`, space, then characters | Separators, size in characters not tokens, overlap |
| `OpenAIEmbeddings` / other embedding wrappers | Batches texts, calls the API, retries | Batch size, retry policy, no caching by default |
| `PGVector` vector store | Creates tables, inserts rows, runs a distance query | Table schema, distance operator, index type (or none) |
| `as_retriever(search_kwargs=...)` | Calls `similarity_search(k=...)` | Fixed k, no filters unless passed, no hybrid |
| `ChatPromptTemplate` | String formatting into messages | Where context goes, how chunks are delimited |
| LCEL pipe (the bar operator) | Composes callables, adds streaming and batching | Execution order, concurrency |
| `StrOutputParser` | Takes `.content` of the message | No validation, no citations |
| Callbacks | Hooks for tracing | What is logged and where |

None of this is magic. It is maybe 200 lines of glue. Writing it yourself makes every decision visible and testable.

## The core in four functions

You need exactly four things: embed, store, retrieve, generate. Everything else (rewriting, re-ranking, caching) plugs in between.

### 1. Embed: plain httpx with batching and retries

Calling the embedding endpoint directly shows you the real contract: a list of strings in, a list of float arrays out, with limits on batch size and tokens.

```python
import asyncio
import os

import httpx
import numpy as np

EMBED_URL = os.environ.get("EMBED_URL", "https://api.openai.com/v1/embeddings")
EMBED_MODEL = os.environ["EMBED_MODEL"]  # example: text-embedding-3-small — check provider's list
BATCH = 64


async def _post_with_retry(client: httpx.AsyncClient, payload: dict, attempts: int = 5) -> dict:
    for i in range(attempts):
        resp = await client.post(EMBED_URL, json=payload)
        if resp.status_code in (429, 500, 502, 503):
            await asyncio.sleep(min(2**i, 30))  # exponential backoff
            continue
        resp.raise_for_status()
        return resp.json()
    raise RuntimeError(f"embedding failed after {attempts} attempts")


async def embed(texts: list[str]) -> np.ndarray:
    headers = {"Authorization": f"Bearer {os.environ['EMBED_API_KEY']}"}
    out: list[list[float]] = []
    async with httpx.AsyncClient(headers=headers, timeout=60) as client:
        for start in range(0, len(texts), BATCH):
            data = await _post_with_retry(client, {"model": EMBED_MODEL, "input": texts[start : start + BATCH]})
            # sort by index: the API contract says results map to inputs by "index"
            out.extend(d["embedding"] for d in sorted(data["data"], key=lambda d: d["index"]))
    vecs = np.asarray(out, dtype=np.float32)
    return vecs / np.linalg.norm(vecs, axis=1, keepdims=True)  # normalize once, cosine == dot
```

Normalizing at write time means cosine similarity becomes a plain dot product, which keeps in-memory numpy search and tests simple. pgvector's cosine operator ranks normalized and raw vectors the same way, so nothing breaks in the database.

### 2. Store and 3. Retrieve: SQL you can read

With psycopg 3 and the `pgvector` adapter, the store is the `documents` and `chunks` schema you built in `03-pgvector/` (Postgres from the `pgvector/pgvector:pg17` image), and the retriever is a query. You see the distance operator, the filters and the index that will be used.

```python
import psycopg
from pgvector.psycopg import register_vector
from psycopg.rows import dict_row

# Schema from 03-pgvector: documents(doc_id, doc_type, jurisdiction, effective_date, is_current, content_hash)
# and chunks(chunk_id, doc_id, parent_id, section, page, content, embedding_model, embedding vector(1024), tsv),
# with an HNSW index on (embedding vector_cosine_ops) and a GIN index on tsv.

VECTOR_SQL = """
SELECT c.chunk_id, c.parent_id, c.doc_id, c.section, c.page, c.content,
       1 - (c.embedding <=> %(q)s) AS score
FROM chunks c JOIN documents d USING (doc_id)
WHERE d.is_current AND d.jurisdiction = ANY(%(jur)s)
  AND (%(doc_type)s::text IS NULL OR d.doc_type = %(doc_type)s)
  AND c.embedding_model = %(model)s
ORDER BY c.embedding <=> %(q)s
LIMIT %(n)s
"""

KEYWORD_SQL = """
SELECT c.chunk_id, c.parent_id, c.doc_id, c.section, c.page, c.content,
       ts_rank_cd(c.tsv, query) AS score
FROM chunks c JOIN documents d USING (doc_id), websearch_to_tsquery('english', %(text)s) AS query
WHERE c.tsv @@ query AND d.is_current AND d.jurisdiction = ANY(%(jur)s)
  AND (%(doc_type)s::text IS NULL OR d.doc_type = %(doc_type)s)
ORDER BY score DESC
LIMIT %(n)s
"""


def connect(dsn: str) -> psycopg.Connection:
    conn = psycopg.connect(dsn, autocommit=True)
    register_vector(conn)
    return conn


def search(conn, sql: str, params: dict) -> list[dict]:
    with conn.cursor(row_factory=dict_row) as cur:
        cur.execute(sql, params)
        return cur.fetchall()


def rrf(*ranked_lists: list[dict], k: int = 60) -> list[dict]:
    scores: dict[str, float] = {}
    rows: dict[str, dict] = {}
    for lst in ranked_lists:
        for rank, row in enumerate(lst, start=1):
            scores[row["chunk_id"]] = scores.get(row["chunk_id"], 0.0) + 1.0 / (k + rank)
            rows[row["chunk_id"]] = row
    return [rows[cid] for cid in sorted(scores, key=scores.get, reverse=True)]
```

`<=>` is pgvector's cosine *distance* (0 means identical), so ascending order puts the most similar chunk first, and `1 - distance` gives a readable similarity. The HNSW index from `03-pgvector/` was built with `vector_cosine_ops`, so the query must use `<=>`. Switch to `<#>` (inner product) or `<->` (L2) and Postgres silently falls back to a sequential scan. A framework would not tell you that.

Two more decisions are now explicit. The metadata filters (`is_current`, `jurisdiction`, `doc_type`) sit inside each leg, before fusion, exactly as in `04-hybrid/`; filtering after fusion would let out-of-scope chunks push valid ones out of the 40 candidates. And `embedding_model = %(model)s` guarantees you never compare a query vector with vectors from a different model during a migration.

### Parent-child retrieval by hand

Lesson 04 introduced parent-child retrieval: match on small child chunks, send their full parent section to the LLM. LangChain's `ParentDocumentRetriever` hides a docstore, an id key in metadata and a dedup step. By hand, it is one table, one column and one function.

```sql
-- Parents are full sections; children are the small chunks you already embed.
CREATE TABLE IF NOT EXISTS parents (
  parent_id  text PRIMARY KEY,
  doc_id     text NOT NULL REFERENCES documents(doc_id) ON DELETE CASCADE,
  section    text NOT NULL,
  content    text NOT NULL            -- cap at roughly 1,500 tokens at ingestion
);
ALTER TABLE chunks ADD COLUMN IF NOT EXISTS parent_id text REFERENCES parents(parent_id);
```

```python
PARENTS_SQL = "SELECT parent_id, doc_id, section, content FROM parents WHERE parent_id = ANY(%(ids)s)"


def expand_to_parents(conn, children: list[dict], max_parents: int = 4) -> list[dict]:
    """children arrive best-first (after RRF and re-ranking). Keep that order, dedupe parents."""
    order: list[str] = []
    for c in children:
        pid = c["parent_id"] or c["chunk_id"]       # chunks without a parent stand alone
        if pid not in order:
            order.append(pid)
        if len(order) == max_parents:
            break
    parents = {r["parent_id"]: r for r in search(conn, PARENTS_SQL, {"ids": order})}
    out: list[dict] = []
    for pid in order:
        matched = [c for c in children if (c["parent_id"] or c["chunk_id"]) == pid]
        base = parents.get(pid) or matched[0]       # fall back to the child itself
        out.append({**base, "chunk_id": pid, "matched_children": [c["chunk_id"] for c in matched]})
    return out
```

What you now control, and what the framework chose for you: the order of parents follows the best child (not the parent's own score), duplicates collapse when several children share a section, parents are capped so context does not explode, and `matched_children` survives so the UI can highlight the exact sentence that matched while the citation points to the whole section. Measure it on the golden set: parent expansion usually helps answers that need the surrounding conditions of a rule, and costs more input tokens per request.

### 4. Generate: the SDK, a prompt you own, and validation

```python
from anthropic import AsyncAnthropic

client = AsyncAnthropic()

SYSTEM = """Answer using ONLY the chunks. Cite chunk ids in square brackets after each sentence,
like [uw-4.2-a1f3]. If the chunks do not contain the answer, reply exactly: NOT_FOUND."""


async def generate(question: str, chunks: list[dict]) -> dict:
    context = "\n\n".join(f'<chunk id="{c["chunk_id"]}">\n{c["content"]}\n</chunk>' for c in chunks)
    msg = await client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=700,
        system=SYSTEM,
        messages=[{"role": "user", "content": f"{context}\n\nQuestion: {question}"}],
    )
    text = msg.content[0].text.strip()
    return {"answer": text, "found": text != "NOT_FOUND", "usage": msg.usage.model_dump()}
```

Wiring it together is a plain async function: embed the query, run both SQL searches with 40 candidates each, fuse with `rrf`, optionally re-rank, expand to parents, generate, validate citations (lesson 13), log a trace. No hidden state.

## What you gain and what you lose

**You gain:**

- Every SQL query, prompt and retry policy is visible in a diff and in code review.
- Fewer dependencies and faster cold starts (relevant for Lambda in Module 5).
- Precise control: token-based chunking, custom filters, the exact citation format you want.
- Stack traces that point to your code, not to five layers of `Runnable`.

**You lose:**

- Ready-made integrations (dozens of loaders, vector stores, model providers).
- Built-in streaming and batching across a chain, and tracing hooks that LangSmith reads automatically.
- Community patterns and examples that assume the framework.

A pragmatic stance many teams take: write the core retrieval and generation path yourself (it is small and business-critical), and use framework pieces at the edges (document loaders, agent orchestration with LangGraph) where they save real time.

## Common mistakes

- **Forgetting to sort embedding results by index.** Most APIs return them in order, but the contract is the `index` field. Relying on order is a latent bug.
- **Dimension mismatches.** The `vector(N)` column must match the model's output dimension. Switching models means a new column or table, plus re-embedding.
- **Operator and index mismatch.** Using `<#>` (inner product) in the query with an index built for `vector_cosine_ops` skips the index. Check with `EXPLAIN ANALYZE`.
- **No retries or backoff.** Ingestion of 10,000 chunks will hit a 429. Without backoff, you get partial indexes.
- **Rebuilding a framework.** If your "no framework" code grows plugin registries and abstract base classes, stop. Keep it boring.
- **String-building SQL.** Always use parameters (`%(q)s`), never f-strings, even for internal tools.

## How this shows up in interviews

<InterviewQuestion question="What does LangChain actually do in a basic RAG chain, and when would you not use it?" level="mid">

It wraps four steps: splitting documents, calling an embeddings API in batches, storing and querying vectors through a vector-store class, and formatting a prompt then calling a chat model. LCEL composes those steps and adds streaming and tracing hooks. I would skip it for the core path when I need full control over SQL, filters, chunking by tokens, citation formats, or when I want minimal dependencies and cold-start time, for example on Lambda. I would still use it, or LangGraph, at the edges where integrations save time.

</InterviewQuestion>

<InterviewQuestion question="Your pgvector query got 50x slower after a change. What do you check?" level="senior">

I run `EXPLAIN ANALYZE` to see whether the HNSW or IVFFlat index is used. Common causes: the distance operator in the query no longer matches the index operator class (cosine vs inner product), a new metadata filter that makes the planner choose a sequential scan, or a missing index after a migration. For filtered ANN queries I check selectivity; very selective filters can make the index return too few rows, so I may raise `hnsw.ef_search`, enable iterative index scans in recent pgvector versions, or use partial indexes per product.

</InterviewQuestion>
