## Company context

Harborline Mutual is a regional property and casualty insurer (fictional) with about 1,200 employees and 400,000 active homeowner and auto policies. It handles roughly 6,000 new claims per month. Each claim arrives as a bundle of PDFs: a **first notice of loss (FNOL) form**, **adjuster field reports**, **repair estimates**, photos with captions, and the relevant **policy document** with its endorsements.

Today, intake staff open each PDF and type 15–20 fields into the claims system. It takes 12–20 minutes per claim and errors are common (wrong policy number, missed date of loss). When adjusters need to know "is this covered?", they search 40-page policy PDFs by hand.

Harborline already lands documents in cloud storage and runs its data warehouse on Databricks. Security insists that claim data stays inside the governed platform, that access is auditable, and that no personal data is sent to systems outside approved endpoints.

## Business goal

Cut manual intake time by at least 60% by pre-filling structured claim fields from documents, and give adjusters a cited Q&A assistant over each claim's documents and policy. Success in a 4-week pilot means intake staff only review and correct extracted fields, and adjusters use the assistant for coverage lookups with no unsupported coverage statements found in QA review.

## Functional requirements

1. **Ingestion.** Claim PDFs land in a Unity Catalog Volume (`/Volumes/<catalog>/claims/raw_docs/`). An incremental job (Auto Loader with `binaryFile`, `availableNow` trigger) loads new files into a bronze Delta table with path, size, modification time and `claim_id` parsed from the folder name.
2. **Parsing and chunking.** Parse each PDF to text per page (a Python parser or `ai_parse_document` if available), classify document type (`fnol`, `adjuster_report`, `estimate`, `policy`, `endorsement`), and write a silver table. Chunk to a gold table with deterministic `chunk_id`, `claim_id`, `doc_id`, `doc_type`, `page`, `content` and lineage columns (`parser_version`, `chunker_config`, `run_id`). Change Data Feed enabled, primary key set.
3. **PII handling.** Detect and pseudonymize names, phone numbers, emails and SSNs in text sent to the Q&A index and logs. Keep the original values only in the governed extraction table that intake needs, restricted by UC grants.
4. **Vector Search.** Delta Sync index on the gold chunks with managed embeddings, `TRIGGERED` sync after each ingestion run, filterable by `claim_id` and `doc_type`.
5. **Extraction chain.** For each claim, extract into a Pydantic model and write to `claims.extracted_fields`:
   - `claim_number`, `policy_number`, `date_of_loss`, `date_reported`, `loss_type` (enum: water, fire, wind, theft, collision, liability, other), `loss_location`, `claimed_amount`, `estimate_total`, `insured_name`, `adjuster_name`, `police_report_number` (nullable)
   - a per-field `source` (`doc_id`, `page`) and `confidence` (`high` | `low`)
   - validation: dates parse, `date_of_loss` not after `date_reported`, policy number matches `POL-` plus 8 digits, amounts non-negative. Failing fields are set to `null` with `confidence = low`, never guessed.
6. **Q&A chain.** Given `claim_id` and a question, retrieve only that claim's chunks plus its policy, answer with citations `[doc_id p.N]`, and say "not enough information" when the documents do not answer it. It must never state that a claim is approved or will be paid.
7. **Evaluation.** MLflow traces for both chains. `mlflow.genai.evaluate` with:
   - extraction: custom code scorers for field-level exact match (normalized) on a golden set of at least 40 claims
   - Q&A: `Correctness`, `RetrievalGroundedness`, `RelevanceToQuery`, `Safety`, a `Guidelines` scorer for the "no approval promises" rule, and a citation code scorer, on at least 40 golden questions
8. **Serving.** Log the Q&A agent with models from code and declared resources, register it in Unity Catalog, and deploy with `agents.deploy` (or a Model Serving endpoint). Inference tables or trace logging enabled. Extraction runs as a batch job (or `ai_query` over the silver table).
9. **Monitoring.** A SQL dashboard or notebook over inference/extraction tables: requests per day, p95 latency, low-confidence field rate, thumbs-down rate.

## Non-functional requirements

| Area | Target |
|---|---|
| Q&A latency | p95 under 6 s end to end for a single question |
| Extraction throughput | A 10-page claim bundle extracted in under 60 s in batch |
| Extraction accuracy | ≥ 95% field-level exact match on key fields (claim number, policy number, date of loss, loss type, claimed amount); ≥ 85% on all fields |
| Q&A quality | Groundedness ≥ 0.90, correctness ≥ 0.80, zero "approval promise" violations on the golden set |
| Cost | Measure and report cost per 1k documents processed and per 1k questions answered, from token usage and current provider/platform prices. Set a target after the first measurement and explain it |
| Freshness | New documents searchable within 30 minutes of landing (scheduled job) |
| Governance | All tables, Volume, index and model in one UC schema; apps use a service principal; no personal tokens in code |
| Privacy | PII scrubber recall ≥ 0.95 on a labeled sample of 50 snippets |

## Out of scope

- Fraud detection or claim approval decisions.
- OCR model training. Use an off-the-shelf parser; scanned images may be skipped and logged.
- Integration with the real claims management system — write to Delta tables only.
- A custom web front end. The Review App (or a simple notebook/Streamlit demo) is enough.
- Fine-tuning. Document why you did not need it.

## Acceptance criteria

- Re-running ingestion on the same files produces no duplicate rows (proved by a test or a query in the README).
- Updating one document and re-running the pipeline updates its chunks and removes stale ones from the index.
- Extraction meets the accuracy targets on the golden set, reported per field from an MLflow run.
- Q&A meets groundedness, correctness and safety targets; violations are listed and explained.
- Q&A retrieval is scoped by `claim_id`: a test shows a question about claim A never returns chunks from claim B.
- p95 latency and cost per 1k are measured and reported, with the method explained.
- Endpoint or service is reachable and traced; inference logging verified with a query.
- No secrets in the repo; access via service principal or environment configuration.

## How to present this in an interview

Lead with the business problem in one sentence: "An insurer spent 15 minutes per claim typing fields from PDFs; I built a governed pipeline that extracts them at 95%+ field accuracy and answers adjuster questions with citations."

Then walk the diagram left to right, pausing on decisions:

- **Why Delta Sync with TRIGGERED mode** — documents arrive in batches; 30-minute freshness doesn't justify continuous sync cost.
- **Why extraction is a batch job and Q&A is an endpoint** — different latency needs and cost profiles.
- **How you prevent cross-claim leakage** — `claim_id` filter derived from the request context, plus a test.
- **How you measured quality** — field-level code scorers for extraction, judges plus a calibrated sample for Q&A, two MLflow runs showing improvement.
- **Where PII lives** — originals only in the restricted extraction table; pseudonyms everywhere else; measured recall.
- **What it costs** — your measured cost per 1k documents and questions, and the biggest lever you found.
- **Why no fine-tuning** — prompting plus validation met the targets; fine-tuning would add retraining and serving cost.

Expect follow-ups like "what breaks at 10x volume?" (parsing throughput, provisioned throughput for the LLM, index size and endpoint sizing) and "how would you catch a regression after a prompt change?" (golden sets as a CI gate plus scheduled scorers on production traces). If you used the local stack, say so directly and show the mapping table — the design reasoning is the same, and interviewers value that honesty.
