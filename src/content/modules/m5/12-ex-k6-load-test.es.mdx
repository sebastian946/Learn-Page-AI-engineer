## Objetivo

Escribe una prueba de carga con k6 para el endpoint de streaming de `mortgage-knowledge-assistant`. Ejecútala contra tu stack de docker-compose con el proveedor mock. Luego escribe un **reporte de resultados** corto y honesto que nombre tu primer cuello de botella. Este es el artefacto que lee un hiring manager: thresholds, números y una explicación clara de qué limita al servicio.

Como SDET ya sabes que una prueba sin aserciones no es una prueba. Aquí las aserciones son los **thresholds**. k6 termina con código distinto de cero cuando uno falla, así que el mismo script puede luego bloquear un deploy.

Objetivo de este ejercicio (ajústalo si tu hardware es pequeño, y dilo en el reporte):

| Métrica | Threshold |
|---|---|
| Carga estable | 10 peticiones/segundo durante 3 minutos |
| `ttft_ms` p95 | menos de 1500 ms (TTFT del mock en 800 ms) |
| `http_req_duration` p95 | menos de 12 s |
| Tasa de errores (HTTP + errores SSE dentro del stream) | menos de 1% |

## Criterios de aceptación

<AcceptanceCriteria>

- [ ] `loadtest/chat_stream.js` usa un executor de **arrival rate** (`ramping-arrival-rate` o `constant-arrival-rate`), no VUs fijos.
- [ ] Métricas custom: `ttft_ms` (Trend), `tokens_per_sec` (Trend), `sse_error_rate` (Rate).
- [ ] Thresholds para TTFT p95, duración p95, `http_req_failed` y `sse_error_rate`. Al menos un threshold usa `abortOnFail`.
- [ ] El TTFT viene del evento `done` reportado por el servidor (o de una extensión SSE). El reporte explica por qué no se usa `timings.waiting` directamente.
- [ ] `loadtest/questions.json` tiene al menos 50 preguntas variadas, para que la caché exacta no domine.
- [ ] El stack corre con `LLM_PROVIDER=mock`, `MOCK_TTFT_MS=800`, `MOCK_TOKENS_PER_SEC=60` desde un archivo override de compose.
- [ ] Se registran dos ejecuciones: caché **desactivada** y caché **activada**.
- [ ] Una **ejecución de estrés** sube por encima del objetivo hasta que un threshold falla. El reporte da la tasa donde se rompió.
- [ ] `loadtest/RESULTS.md` sigue la plantilla de abajo y nombra un cuello de botella con evidencia (spans de tracing, estadísticas de contenedores o logs).
- [ ] Un target `make loadtest` (o `just`/script) ejecuta todo con un solo comando.

</AcceptanceCriteria>

## Pistas

<Hints>
  <Hint>Empieza con una ejecución de humo: `RATE=1` durante 30 segundos. Confirma que cada petición parsea un evento `done` y que `ttft_ms` está cerca de 800 ms. Si el TTFT es mucho mayor a 1 petición por segundo, tienes overhead antes de la llamada al LLM (retrieval, re-ranking, una llamada de embeddings) que debes medir primero.</Hint>
  <Hint>Los thresholds son un objeto con el nombre de la métrica como clave. Usa la forma larga para abortar: `sse_error_rate: [{ threshold: 'rate<0.01', abortOnFail: true, delayAbortEval: '30s' }]`. El delay evita que una falla temprana durante el calentamiento mate la ejecución.</Hint>
  <Hint>Para la ejecución de estrés, cambia a `ramping-arrival-rate` con etapas como 10, 20, 40, 60 peticiones por segundo, dos minutos cada una. Mira `docker stats` y tu UI de tracing lado a lado. Anota la etapa donde el TTFT p95 cruza 1500 ms. Si k6 avisa que faltan VUs, sube `maxVUs`. Ese aviso significa que k6 mismo se volvió el cuello de botella.</Hint>
  <Hint>Cuellos de botella típicos con el mock: el pool de Postgres (busca tiempo esperando para obtener una conexión del pool, o errores `QueuePool limit`), un re-ranker cross-encoder limitado por CPU corriendo en el event loop (CPU al 100%, el TTFT sube para todas las peticiones), o un cliente de Redis síncrono. Encuentra qué span crece con la carga. Ese span es tu respuesta.</Hint>
</Hints>
