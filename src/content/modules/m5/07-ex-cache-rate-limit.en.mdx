## Goal

Your `mortgage-knowledge-assistant` now runs in Docker (exercise 04). Next, make it cheaper and safer under load. You will add:

1. An **exact answer cache** in Redis, keyed by tenant, normalized question, model, prompt version and corpus version.
2. An optional **semantic cache** behind a feature flag (stretch goal).
3. **Per-tenant rate limiting** with two atomic token buckets in Lua: one for requests, one for LLM tokens, with estimate-then-reconcile.
4. **Metrics** for cache hits, misses and rate-limit rejections.

Work on branch `m5/cache-rate-limit`. Time box: 90 minutes for the required parts. The semantic cache is optional.

Why it matters: in exercise 12 you will load test this service. With a cache and limits in place, you will be able to show the difference in p95 latency and cost per 1k requests. That makes a strong README section.

## Acceptance criteria

<AcceptanceCriteria>

- [ ] `docker compose up` starts Redis alongside the API, Postgres and pgvector. The API reads `REDIS_URL` from `Settings`.
- [ ] `POST /v1/chat` and `POST /v1/chat/stream` check the exact cache first. A hit returns in under 50 ms locally and makes no LLM call.
- [ ] The cache key includes tenant id (as prefix), normalized question, model id, prompt version, corpus version and temperature.
- [ ] Only complete, successful answers are cached. Errors, guardrail blocks and interrupted streams are never cached.
- [ ] A streaming cache hit still emits `token`, `citations` and `done` SSE events, in that order.
- [ ] Each tenant (from `X-Tenant-ID`) has a request bucket and a token bucket. Limits come from `Settings`, with an optional per-tenant override map.
- [ ] Bucket updates run in a single Lua script, so concurrent replicas cannot over-admit.
- [ ] Rejected requests return 429 with a `Retry-After` header and a JSON error body. No LLM call is made.
- [ ] After each LLM call, the token bucket is reconciled with real `usage.input_tokens` and `usage.output_tokens`.
- [ ] If Redis is down, the cache fails open (request proceeds) and the limiter falls back to an in-memory limiter. Both log a warning.
- [ ] Prometheus counters exist: `cache_requests_total` with label `result` (hit, miss, semantic_hit) and `rate_limited_total` with labels `tenant` and `bucket`.
- [ ] Tests cover: key changes when prompt or corpus version changes, cache hit skips the LLM, 429 with `Retry-After`, concurrent requests do not exceed the bucket, reconcile refunds over-estimates.
- [ ] Stretch: semantic cache behind `SEMANTIC_CACHE_ENABLED`, scoped by tenant and versions, skipped for questions containing digits.

</AcceptanceCriteria>

## Hints

<Hints>
  <Hint>Start with the cache, not the limiter. Write `cache_key` and three unit tests for it before touching the endpoint. Pure functions are the fastest feedback loop.</Hint>
  <Hint>For the streaming endpoint, wrap the generator: accumulate tokens in a list, and only call `cache.set` after you have yielded the `done` event and the stream finished without exceptions. If the client disconnects, the generator gets cancelled and you never reach the `set` call, which is exactly what you want.</Hint>
  <Hint>For the corpus version, the simplest robust option is a Redis key `corpus_version:{tenant}` that your ingestion job increments with `INCR` after each successful run. Read it once per request. Cache it in-process for 30 seconds if you want to save a round trip.</Hint>
  <Hint>For the fallback limiter, a dict of `tenant -> (tokens, last_ts)` with the same refill math is enough. It is per replica, so the effective limit becomes limit times replicas during a Redis outage. Write that trade-off in your README; it is a good interview talking point.</Hint>
</Hints>
