## Objetivo

Tu `mortgage-knowledge-assistant` ya tiene un workflow de CI del módulo 3: tests unitarios más un eval gate que bloquea un PR si baja el faithfulness. En este ejercicio lo extiendes a un **pipeline de CI/CD** completo. Cada merge a `main` construye una imagen, la despliega en **staging**, ejecuta un smoke test y luego espera aprobación antes de desplegar **la misma imagen** en **producción** sobre ECS Fargate.

¿No tienes cuenta de AWS o no quieres pagar un ALB? Sigue el **camino Fly.io** al final. Los criterios de aceptación son los mismos, excepto los específicos de AWS.

Piénsalo como el pipeline de release de un framework de pruebas que ya mantienes. Construye una vez, promueve el artefacto, pon un gate en cada etapa y falla de forma ruidosa.

El flujo que vas a construir:

```text
PR:    lint -> unit tests -> eval gate (mock + small real sample)
main:  tests -> build image (tag = git SHA) -> push to ECR (OIDC)
       -> deploy staging -> smoke test -> [manual approval] -> deploy prod -> smoke test
```

## Criterios de aceptación

<AcceptanceCriteria>

- [ ] Los PRs ejecutan lint, tests unitarios y el eval gate del módulo 3. Ningún job de deploy corre en PRs.
- [ ] En push a `main`, la imagen se construye **una sola vez**, se etiqueta con `github.sha` y se sube a ECR.
- [ ] La autenticación con AWS usa **GitHub OIDC** (`aws-actions/configure-aws-credentials` con `role-to-assume`). No existen llaves de AWS de larga duración en los secretos de GitHub.
- [ ] La task definition vive en `infra/taskdef.json`. CI le inyecta la imagen con `aws-actions/amazon-ecs-render-task-definition`.
- [ ] El deploy usa `aws-actions/amazon-ecs-deploy-task-definition` con `wait-for-service-stability: true`.
- [ ] Existen dos **environments** de GitHub: `staging` y `production`. `production` requiere un reviewer.
- [ ] Producción despliega exactamente el digest de imagen que pasó staging. No reconstruye.
- [ ] Un smoke test corre después de cada deploy: `/healthz` devuelve 200, y una llamada a `/v1/chat/stream` devuelve al menos un evento `token` y un evento `done`.
- [ ] El servicio ECS tiene el deployment circuit breaker con rollback activado.
- [ ] `concurrency` impide que dos deploys al mismo environment corran a la vez.
- [ ] El README tiene una sección "Deployment" con el diagrama del pipeline y cómo hacer rollback manual.

</AcceptanceCriteria>

### Camino Fly.io

Si eliges Fly.io, reemplaza los pasos de ECR/ECS por `superfly/flyctl-actions/setup-flyctl` y dos apps (`mka-staging`, `mka-prod`). Construye una vez con `fly deploy --build-only --push --image-label $GITHUB_SHA` contra staging. Luego despliega ambas apps con `fly deploy --image registry.fly.io/<app>:<sha>`. Guarda `FLY_API_TOKEN` como **secreto de environment**, con alcance por environment. OIDC no aplica, pero las reglas de protección de environments sí.

## Pistas

<Hints>
  <Hint>Empieza por IAM, no por el YAML. Crea un identity provider OIDC de IAM para `token.actions.githubusercontent.com`. Luego crea un rol cuya trust policy restrinja el claim `sub` a tu repo y environment, por ejemplo `repo:<tu-usuario>/mortgage-knowledge-assistant:environment:production`.</Hint>
  <Hint>El rol de deploy necesita push a ECR y `ecs:RegisterTaskDefinition`, `ecs:UpdateService`, `ecs:DescribeServices`. También necesita `iam:PassRole` sobre el task execution role y el task role. Que falte `PassRole` es la falla más común en el paso de registro.</Hint>
  <Hint>El render son dos pasos. `amazon-ecs-render-task-definition` recibe `task-definition: infra/taskdef.json`, `container-name: api` e `image`. Su output `task-definition` alimenta `amazon-ecs-deploy-task-definition` junto con `service`, `cluster` y `wait-for-service-stability: true`. Guarda los nombres de cluster y servicio en variables de environment (`vars.ECS_CLUSTER`, `vars.ECS_SERVICE`) para que el mismo job sirva en ambos environments.</Hint>
  <Hint>Para promover el mismo artefacto, pasa `needs.build.outputs.image` a ambos jobs de deploy. Para ser estricto, saca el digest de `build-push-action` (`steps.<id>.outputs.digest`) y despliega `repo@sha256:...`. Staging y prod suelen vivir en cuentas distintas. En ese caso, da a la cuenta de prod acceso de pull al repo de ECR con una repository policy, o replica la imagen.</Hint>
</Hints>
