## What is special about Python AI images

You know Docker. The question here is narrower: why do Python AI images end up at 3–8 GB, take 10 minutes to build, and still break in production?

Three reasons:

1. **Heavy dependencies.** `torch`, `transformers`, `sentence-transformers`, `numpy`, `pyarrow` and PDF parsers pull hundreds of megabytes of wheels. Installing `torch` from the default index on Linux pulls the CUDA build, often over 2 GB, even if you only run on CPU.
2. **Build tools leak into the runtime.** Some packages compile C extensions. If you install `gcc` and headers in the final image, they ship to production.
3. **Model weights.** A local cross-encoder or embedding model adds 100 MB to several GB. Downloading it at container start makes cold starts slow and ties startup to Hugging Face availability.

The fix is the usual toolkit applied with discipline: multi-stage builds, a lockfile, cache mounts, a slim base, a non-root user, and an explicit decision about where weights live.

## Decide first: do you need ML libraries in the image at all?

For `mortgage-knowledge-assistant`, generation and embeddings are API calls. The only local model might be the cross-encoder re-ranker from Module 2. Options:

| Option | Image impact | Trade-off |
|---|---|---|
| Hosted re-ranker API (for example Cohere Rerank) | None | Per-call cost, extra network hop |
| Local cross-encoder on CPU with `torch` CPU wheels | +700 MB to 1 GB | Fixed cost, adds 50–200 ms CPU per request |
| Separate re-ranker service | API image stays small | One more service to deploy |

An API-only image can be under 250 MB. Adding CPU `torch` pushes it toward 1 GB. Adding the CUDA build pushes it over 3 GB. Make that choice consciously, and write it in the README.

If you do need `torch` on CPU, point uv at the CPU index in `pyproject.toml`:

```toml
[[tool.uv.index]]
name = "pytorch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true

[tool.uv.sources]
torch = { index = "pytorch-cpu" }
```

## A production Dockerfile with uv

uv resolves and installs much faster than pip, and `uv.lock` gives reproducible installs. This Dockerfile uses two stages: a builder that creates a virtualenv, and a runtime that copies only the virtualenv and the code.

```dockerfile
# syntax=docker/dockerfile:1.7
ARG PYTHON_VERSION=3.12

FROM python:${PYTHON_VERSION}-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:0.5 /uv /usr/local/bin/uv
ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_PYTHON_DOWNLOADS=never
WORKDIR /app

# 1) Dependencies only: this layer is cached until the lockfile changes
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --frozen --no-install-project --no-dev

# 2) Project code
COPY app ./app
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev

FROM python:${PYTHON_VERSION}-slim AS runtime
RUN groupadd --system app && useradd --system --gid app --home /app app
WORKDIR /app
COPY --from=builder --chown=app:app /app /app
ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1
USER app
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --start-period=20s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz', timeout=2)"
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--proxy-headers"]
```

What each piece buys you:

- **`--mount=type=cache`** keeps the uv download cache between builds on the same builder. Changing one line of code does not re-download wheels. In CI, pair it with BuildKit cache export (`cache-to: type=gha`), which you will see in the CI/CD lesson.
- **`--no-install-project` first, then the code.** The expensive dependency layer depends only on `pyproject.toml` and `uv.lock`. Editing `app/` invalidates only the cheap layer.
- **`UV_COMPILE_BYTECODE=1`** precompiles `.pyc` files. Startup is faster, which matters for autoscaling and cold starts.
- **`--frozen`** fails the build if the lockfile is out of date. No silent resolution in CI.
- **Runtime stage has no uv, no compiler, no cache.** Only the venv and code.
- **Non-root user.** Many platforms require it, and it limits blast radius.
- **`HEALTHCHECK` with Python's stdlib.** The slim image has no `curl`. Do not install it just for a health check. Note that ECS ignores the Dockerfile `HEALTHCHECK` and uses the task definition's `healthCheck`; keep both consistent.
- **Exec-form `CMD`.** Uvicorn is PID 1 and receives `SIGTERM` directly, so it can drain in-flight streams on deploy.

If you prefer pip, the same structure works: build wheels in the builder with `pip wheel -r requirements.txt -w /wheels` using a cache mount on `/root/.cache/pip`, then `pip install --no-index --find-links=/wheels` in the runtime.

### Workers and graceful shutdown

LLM endpoints are I/O bound. One uvicorn process with asyncio can hold hundreds of concurrent streams. On ECS or Kubernetes, prefer **one process per container and scale containers**, rather than `--workers 4` inside a container. It makes CPU and memory metrics honest and autoscaling predictable.

Streams can last 30 s. Give the orchestrator a stop timeout longer than your longest stream (ECS `stopTimeout`, Kubernetes `terminationGracePeriodSeconds`), and run uvicorn with `--timeout-graceful-shutdown` so it stops accepting new connections and lets current answers finish.

## Model weights: four strategies

If your service loads a local model, decide where the weights come from:

1. **Bake into the image.** Download in a build stage, copy into the runtime. Fast cold start, fully reproducible, works offline. Image grows by the model size, and every model change is a new image. Good for small models (under ~500 MB) that change rarely.
2. **Download at startup** from S3 or the Hugging Face Hub. Small image, but slow and fragile cold starts, and a dependency on an external service during scale-out. Pin the revision.
3. **Mount a shared volume** (EFS on ECS, a PVC on Kubernetes) pre-populated with weights. Good for large models shared by many tasks. Adds infrastructure.
4. **Separate model server** (a dedicated re-ranker or embedding service, or a managed endpoint like SageMaker or Bedrock). The API image stays small and the model scales independently.

Baking a small model looks like this:

```dockerfile
FROM builder AS weights
ARG RERANKER_MODEL=cross-encoder/ms-marco-MiniLM-L-6-v2
ARG RERANKER_REVISION=main
ENV HF_HOME=/models
RUN /app/.venv/bin/python -c "from huggingface_hub import snapshot_download; \
    snapshot_download('${RERANKER_MODEL}', revision='${RERANKER_REVISION}')"

FROM runtime
COPY --from=weights --chown=app:app /models /models
ENV HF_HOME=/models HF_HUB_OFFLINE=1
```

`HF_HUB_OFFLINE=1` makes the runtime fail loudly if the model is missing, instead of quietly reaching the internet. Pin a commit hash as the revision in real projects, so the image is reproducible.

## .dockerignore matters more than you think

Without it, `COPY . .` ships your `.venv`, `.git`, eval datasets, PDFs and possibly `.env` with real keys into the build context and maybe into the image.

```text
.git
.venv
__pycache__/
*.pyc
.env
.env.*
data/
evals/results/
loadtest/results/
notebooks/
tests/
.pytest_cache/
.github/
```

Prefer explicit `COPY app ./app` over `COPY . .`. It is self-documenting and safer.

## Measuring the result

```bash
docker build -t mka:dev .
docker image ls mka:dev
docker history mka:dev --format "{{.Size}}\t{{.CreatedBy}}" | head -15
docker run --rm mka:dev python -c "import app.main"   # smoke import
docker scout cves mka:dev   # or: trivy image mka:dev
```

`docker history` shows which layer is fat. Typical surprises: a `COPY . .` with data files, a `pip install` without `--no-cache-dir`, or CUDA `torch`.

## Common mistakes

- **Installing CUDA `torch` for a CPU-only service.** Gigabytes of dead weight and slower pulls on every scale-out.
- **`COPY . .` before installing dependencies.** Every code change reinstalls everything. Builds go from 20 s to 5 min.
- **Using Alpine for Python AI.** Many wheels are built for glibc, not musl. You end up compiling `numpy` from source. Use `-slim`.
- **Secrets in build args or `ENV`.** They are visible in `docker history` and image metadata. Use BuildKit `--mount=type=secret` for build-time secrets (like a private index token) and inject runtime secrets from the platform. Next lesson covers this.
- **Downloading models at runtime without pinning.** A new upstream revision changes your outputs silently. Your evals stop meaning anything.
- **Shell-form `CMD`.** `CMD uvicorn ...` runs under `/bin/sh`, which does not forward `SIGTERM`. Deploys cut streams mid-answer.
- **Running as root** and **using `latest` tags** for base images. Pin `python:3.12-slim` (or a digest) and rebuild regularly for patches.

<Callout type="tip" title="SDET angle">
Treat the image as a test artifact. Add a CI step that builds the image, runs it with `LLM_PROVIDER=mock`, hits `/healthz` and one `/v1/chat` call, and fails if the image exceeds a size budget. It is a smoke test for the container, the same way you smoke test a deployed environment.
</Callout>

## How this shows up in interviews

<InterviewQuestion question="Your Python RAG service image is 4 GB and takes 8 minutes to build. How do you fix it?" level="mid">
First measure with `docker history` to find the fat layers. Common causes: CUDA `torch` on a CPU-only service (switch to the CPU wheel index or move the model behind an API), build tools and caches in the runtime (multi-stage: build the venv in a builder, copy only the venv into a slim runtime), and data or `.venv` in the build context (add `.dockerignore`, use explicit `COPY`).

For build time: copy only the lockfile and install dependencies first so that layer is cached, use BuildKit cache mounts for the uv or pip cache, export the layer cache in CI, and use uv instead of pip. Typical result: a few hundred MB and builds under a minute when only code changes.
</InterviewQuestion>

<InterviewQuestion question="Where should model weights live for a containerized service?" level="senior">
It depends on size and change rate. Small, rarely changing models can be baked into the image: fast cold start, reproducible, offline, but bigger images. Large or frequently updated models fit better on a shared volume or in a separate model-serving service, so the API scales independently and images stay small. Downloading at startup is the weakest option: slow, fragile scale-out and an external dependency during incidents. In every case pin the revision and set offline mode in the runtime so you never load an unexpected model version, because a silent model change invalidates your evals.
</InterviewQuestion>
