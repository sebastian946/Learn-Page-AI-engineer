## Why config gets messy in LLM apps

A classic web service has a database URL and a few feature toggles. An LLM service has much more configuration, and much of it changes behavior in ways tests do not catch:

- Provider API keys (Anthropic, OpenAI, Cohere, Bedrock credentials).
- Model ids for primary and fallback models.
- `max_tokens`, temperature, timeouts, retry counts.
- Retrieval parameters: `top_k`, re-ranker on or off, similarity threshold.
- Prompt version, cache TTLs, rate-limit quotas per tenant.
- Database, Redis and tracing endpoints.

Two rules keep this under control:

1. **Config is typed and validated at startup.** A typo in `LLM_TIMEOUT_S` should crash the container on boot, not produce a 500 at 2 a.m.
2. **Secrets never live in code, images or git.** They are injected at runtime by the platform, and they are redacted in logs and traces.

## pydantic-settings: one typed source of truth

`pydantic-settings` reads environment variables (and optionally a `.env` file in development) into a Pydantic v2 model. You get type coercion, validation and defaults in one place.

```python
# app/settings.py
from functools import lru_cache
from typing import Literal

from pydantic import Field, PostgresDsn, RedisDsn, SecretStr, model_validator
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",          # dev only; missing file is fine
        env_file_encoding="utf-8",
        extra="ignore",
    )

    env: Literal["local", "ci", "staging", "prod"] = "local"
    llm_provider: Literal["anthropic", "mock"] = "anthropic"
    anthropic_api_key: SecretStr | None = None

    primary_model: str = "claude-sonnet-5-5"
    fallback_model: str = "claude-haiku-5-5"
    max_output_tokens: int = Field(default=800, ge=64, le=4096)
    llm_timeout_s: float = Field(default=25.0, gt=0, le=120)
    mock_token_delay_ms: int = Field(default=20, ge=0)

    database_url: PostgresDsn
    redis_url: RedisDsn = RedisDsn("redis://localhost:6379/0")
    db_pool_max: int = Field(default=10, ge=1, le=100)

    prompt_version: str = "answer-v3"
    cache_ttl_s: int = 3600

    @model_validator(mode="after")
    def check_provider_key(self) -> "Settings":
        if self.llm_provider == "anthropic" and self.anthropic_api_key is None:
            raise ValueError("ANTHROPIC_API_KEY is required when LLM_PROVIDER=anthropic")
        if self.env == "prod" and self.llm_provider == "mock":
            raise ValueError("mock provider is not allowed in prod")
        return self


@lru_cache
def get_settings() -> Settings:
    return Settings()
```

Notes:

- **`SecretStr`** prints as `**********` in `repr`, logs and tracebacks. You must call `.get_secret_value()` to read it, which makes accidental leaks visible in code review.
- **Field names map to env vars** case-insensitively: `database_url` reads `DATABASE_URL`. Use `env_prefix="MKA_"` if you share a host with other services.
- **Cross-field validation** catches dangerous combinations, like the mock provider in prod.
- **`lru_cache`** means settings are parsed once. In tests, override with FastAPI dependency overrides or call `get_settings.cache_clear()` after setting env vars with `monkeypatch`.
- **`env_file` is a dev convenience.** In containers, the platform sets real environment variables, which take precedence over the file. The `.env` file must be in `.gitignore` and `.dockerignore`. Commit a `.env.example` with fake values instead.

Fail fast on boot. In `lifespan`, call `get_settings()` first. If validation fails, the process exits with a clear error and the orchestrator marks the deploy as failed before it takes traffic. That is exactly what you want: a bad config should never reach users.

## Config vs secrets vs prompts

Not all settings deserve the same treatment:

| Kind | Examples | Where it lives |
|---|---|---|
| Non-secret config | model ids, timeouts, `top_k` | Env vars in the task definition, or SSM Parameter Store `String` |
| Secrets | API keys, DB password | AWS Secrets Manager or SSM `SecureString`, injected at runtime |
| Fast-changing behavior | prompt version, rollout percentage | Feature flag service or config table (lesson 14) |

Changing a model id is a behavior change. It should go through the same review and eval gate as code. Keeping it in versioned config (task definition in IaC, or a parameter with change history) gives you an audit trail.

## Secrets on AWS: inject, don't fetch (usually)

Two AWS services store secrets:

- **Secrets Manager.** Built for secrets: rotation support (native for RDS), cross-account sharing, versioning. Priced per secret per month plus API calls.
- **SSM Parameter Store.** Hierarchical parameters (`/mka/prod/database_url`). `SecureString` values are encrypted with KMS. Standard parameters have no storage charge. No built-in rotation.

A reasonable default: DB credentials and provider API keys in Secrets Manager; non-secret config in Parameter Store or plain env vars.

### Option A: ECS injects secrets as env vars (recommended)

ECS can resolve secrets at task start and expose them as environment variables. Your code just reads env vars through pydantic-settings, and never imports boto3 for config.

```json
{
  "containerDefinitions": [
    {
      "name": "api",
      "image": "123456789012.dkr.ecr.us-east-1.amazonaws.com/mka:3f9c2e1",
      "environment": [
        { "name": "ENV", "value": "prod" },
        { "name": "PRIMARY_MODEL", "value": "claude-sonnet-5-5" }
      ],
      "secrets": [
        {
          "name": "ANTHROPIC_API_KEY",
          "valueFrom": "arn:aws:secretsmanager:us-east-1:123456789012:secret:mka/prod/anthropic-AbCdEf"
        },
        {
          "name": "DATABASE_URL",
          "valueFrom": "arn:aws:ssm:us-east-1:123456789012:parameter/mka/prod/database_url"
        }
      ]
    }
  ]
}
```

The **task execution role** needs `secretsmanager:GetSecretValue` and `ssm:GetParameters` on exactly those ARNs (plus `kms:Decrypt` if you use a customer-managed key). The **task role** (what your code runs as) does not need them at all. Least privilege by design.

Trade-off: values are read at task start. After rotating a key, you must restart tasks (force a new deployment) to pick it up.

### Option B: fetch at runtime with caching

If you need rotation without restarts, or many secrets per tenant, fetch from Secrets Manager in code and cache with a TTL:

```python
import json
import time

import boto3

_cache: dict[str, tuple[float, dict]] = {}
_client = boto3.client("secretsmanager")


def get_secret(secret_id: str, ttl_s: int = 300) -> dict:
    now = time.monotonic()
    hit = _cache.get(secret_id)
    if hit and now - hit[0] < ttl_s:
        return hit[1]
    value = json.loads(_client.get_secret_value(SecretId=secret_id)["SecretString"])
    _cache[secret_id] = (now, value)
    return value
```

This is a sync call; call it at startup or in a threadpool, not on every request in the event loop. AWS also offers a caching client library and a Secrets Manager agent sidecar for the same purpose. Per-tenant API keys (customers bringing their own provider key) are a common reason to need this pattern.

## Never in images, never in logs

Places secrets leak in LLM apps:

- **Docker `ENV` or `ARG`.** Visible in `docker history` and `docker inspect`. Anyone who can pull the image can read them.
- **`COPY . .` with a `.env`.** The file is now in a layer forever, even if a later layer deletes it.
- **CI logs.** `echo $ANTHROPIC_API_KEY` for debugging. GitHub masks registered secrets, but not values derived from them.
- **Traces and prompts.** Tracing tools capture full request headers and prompt inputs. If a user pastes a password into chat, or your code puts a token in a prompt, it lands in your observability vendor. Configure redaction.
- **Exception messages.** A connection error that prints the full DSN with password.

For build-time secrets (a private package index token), use BuildKit secret mounts. The secret is available only during that `RUN` and is not stored in any layer:

```dockerfile
RUN --mount=type=secret,id=pypi_token,env=UV_INDEX_PRIVATE_PASSWORD \
    uv sync --frozen --no-dev
```

```bash
docker build --secret id=pypi_token,env=PYPI_TOKEN -t mka:dev .
```

In CI, add secret scanning (GitHub push protection, gitleaks) so a committed key is blocked before merge. If a key leaks anyway: revoke it at the provider first, then rotate, then clean history. Assume it was used.

## Local development without real keys

Make the default developer path not need production secrets at all:

```bash
# .env.example (committed)
ENV=local
LLM_PROVIDER=mock
DATABASE_URL=postgresql://mka:mka@localhost:5432/mka
REDIS_URL=redis://localhost:6379/0
# ANTHROPIC_API_KEY=sk-ant-...  set your own personal dev key if you need real answers
```

With `LLM_PROVIDER=mock`, tests, docker-compose and load tests run with zero cost and zero secrets. Developers who need real answers use their own scoped dev key with a low spend limit set in the provider console.

## Common mistakes

- **Reading `os.environ` all over the codebase.** No validation, no types, no single place to see what the service needs. Centralize in `Settings`.
- **Defaults that are only safe in dev.** For example, defaulting `llm_provider` to `mock` and forgetting to override in prod, or a default DB URL pointing at localhost. Prefer required fields for anything environment-specific.
- **Using `str` for secrets.** One `logger.info(settings)` dumps every key. Use `SecretStr`.
- **Giving the task role broad `secretsmanager:*`.** Scope to exact ARNs, and use the execution role for injection.
- **Forgetting that injected secrets are read once.** Rotating a key without redeploying leaves old tasks with a revoked key and causes a wave of 401s.
- **Shared keys across environments.** Staging load tests then consume prod rate limits and budget. Use separate provider keys (or workspaces) per environment with separate spend limits.

<Callout type="tip" title="SDET angle">
Write tests for the config itself: invalid values fail validation, prod rejects the mock provider, and `repr(Settings(...))` never contains the raw key. These are cheap unit tests that prevent expensive incidents.
</Callout>

## How this shows up in interviews

<InterviewQuestion question="How do you manage secrets for an LLM service running on ECS?" level="mid">
Store provider keys and DB credentials in AWS Secrets Manager (or SSM `SecureString`). Reference them in the task definition's `secrets` block so ECS injects them as environment variables at task start. Grant only the task execution role `GetSecretValue` on those specific ARNs. The app reads env vars through pydantic-settings with `SecretStr`, so values are validated at startup and masked in logs. Nothing secret goes into the image, build args, or git; `.env` is in `.gitignore` and `.dockerignore`. Rotation means updating the secret and forcing a new deployment, or fetching at runtime with a TTL cache if you need rotation without restarts.
</InterviewQuestion>

<InterviewQuestion question="Someone pushed an Anthropic API key to a public repo. What do you do?" level="senior">
Treat it as compromised immediately. First revoke the key in the provider console, not just delete the commit: bots scan public repos within minutes. Issue a new key, store it in Secrets Manager, and force a redeploy so tasks pick it up. Check usage and billing for unexpected spend since the push. Then clean up: remove it from history if policy requires, and add prevention (push protection or gitleaks in CI, pre-commit hooks, `.env` patterns ignored). Finally, write a short blameless postmortem and check whether the key had broader scope than needed, for example one key shared by all environments.
</InterviewQuestion>
