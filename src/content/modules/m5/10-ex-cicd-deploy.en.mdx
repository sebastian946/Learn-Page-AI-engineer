## Goal

Your `mortgage-knowledge-assistant` already has a CI workflow from Module 3: unit tests plus an eval gate that blocks a PR if faithfulness drops. In this exercise you extend it into a full **CI/CD pipeline**. Every merge to `main` builds one image, deploys it to **staging**, smoke-tests it, and then waits for approval before deploying the **same image** to **production** on ECS Fargate.

No AWS account, or you don't want to pay for an ALB? Follow the **Fly.io path** at the end. The acceptance criteria are the same except for the AWS-specific items.

Think of it like a release pipeline for a test framework you already maintain. Build once, promote the artifact, gate each stage, and fail loudly.

The flow you are building:

```text
PR:    lint -> unit tests -> eval gate (mock + small real sample)
main:  tests -> build image (tag = git SHA) -> push to ECR (OIDC)
       -> deploy staging -> smoke test -> [manual approval] -> deploy prod -> smoke test
```

## Acceptance criteria

<AcceptanceCriteria>

- [ ] PRs run lint, unit tests and the Module 3 eval gate. No deploy jobs run on PRs.
- [ ] On push to `main`, the image is built **once**, tagged with `github.sha`, and pushed to ECR.
- [ ] AWS authentication uses **GitHub OIDC** (`aws-actions/configure-aws-credentials` with `role-to-assume`). No long-lived AWS keys exist in GitHub secrets.
- [ ] The task definition lives in `infra/taskdef.json`. CI renders the image into it with `aws-actions/amazon-ecs-render-task-definition`.
- [ ] Deploy uses `aws-actions/amazon-ecs-deploy-task-definition` with `wait-for-service-stability: true`.
- [ ] Two GitHub **environments** exist: `staging` and `production`. `production` requires a reviewer.
- [ ] Production deploys the exact image digest that passed staging. It does not rebuild.
- [ ] A smoke test runs after each deploy: `/healthz` returns 200, and one `/v1/chat/stream` call returns at least one `token` event and a `done` event.
- [ ] The ECS service has the deployment circuit breaker with rollback enabled.
- [ ] `concurrency` prevents two deploys to the same environment from running at once.
- [ ] README has a "Deployment" section with the pipeline diagram and how to roll back manually.

</AcceptanceCriteria>

  id-token: write   # required for OIDC
  contents: read

env:
  AWS_REGION: us-east-1
  ECR_REPOSITORY: mortgage-knowledge-assistant

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      image: ${{ steps.meta.outputs.image }}

      - uses: actions/checkout@v4

### Fly.io path

If you choose Fly.io, replace the ECR/ECS steps with `superfly/flyctl-actions/setup-flyctl` and two apps (`mka-staging`, `mka-prod`). Build once with `fly deploy --build-only --push --image-label $GITHUB_SHA` against staging. Then deploy both apps with `fly deploy --image registry.fly.io/<app>:<sha>`. Store `FLY_API_TOKEN` as an **environment secret**, scoped per environment. OIDC does not apply, but environment protection rules still do.

## Hints

<Hints>
  <Hint>Start with IAM, not YAML. Create an IAM OIDC identity provider for `token.actions.githubusercontent.com`. Then create a role whose trust policy restricts the `sub` claim to your repo and environment, for example `repo:<you>/mortgage-knowledge-assistant:environment:production`.</Hint>
  <Hint>The deploy role needs ECR push and `ecs:RegisterTaskDefinition`, `ecs:UpdateService`, `ecs:DescribeServices`. It also needs `iam:PassRole` on the task execution role and task role. Missing `PassRole` is the most common failure at the register step.</Hint>
  <Hint>Rendering is two steps. `amazon-ecs-render-task-definition` takes `task-definition: infra/taskdef.json`, `container-name: api` and `image`. Its `task-definition` output feeds `amazon-ecs-deploy-task-definition` along with `service`, `cluster` and `wait-for-service-stability: true`. Keep cluster and service names in environment variables (`vars.ECS_CLUSTER`, `vars.ECS_SERVICE`) so the same job works for both environments.</Hint>
  <Hint>To promote the same artifact, pass `needs.build.outputs.image` to both deploy jobs. To be strict, output the digest from `build-push-action` (`steps.<id>.outputs.digest`) and deploy `repo@sha256:...`. Staging and prod usually live in different accounts. In that case, give the prod account pull access to the ECR repo with a repository policy, or replicate the image.</Hint>
</Hints>
