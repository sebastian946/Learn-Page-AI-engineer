## Goal

Write a k6 load test for the `mortgage-knowledge-assistant` streaming endpoint. Run it against your docker-compose stack with the mock provider. Then write a short, honest **results report** that names your first bottleneck. This is the artifact a hiring manager reads: thresholds, numbers, and a clear explanation of what limits the service.

As an SDET you already know a test without assertions is not a test. Here the assertions are **thresholds**. k6 exits non-zero when one fails, so the same script can later gate a deploy.

Target for this exercise (adjust if your hardware is small, and say so in the report):

| Metric | Threshold |
|---|---|
| Steady load | 10 requests/second for 3 minutes |
| `ttft_ms` p95 | under 1500 ms (mock TTFT set to 800 ms) |
| `http_req_duration` p95 | under 12 s |
| Error rate (HTTP + in-stream SSE errors) | under 1% |

## Acceptance criteria

<AcceptanceCriteria>

- [ ] `loadtest/chat_stream.js` uses an **arrival-rate** executor (`ramping-arrival-rate` or `constant-arrival-rate`), not fixed VUs.
- [ ] Custom metrics: `ttft_ms` (Trend), `tokens_per_sec` (Trend), `sse_error_rate` (Rate).
- [ ] Thresholds for p95 TTFT, p95 duration, `http_req_failed` and `sse_error_rate`. At least one threshold uses `abortOnFail`.
- [ ] TTFT comes from the server-reported `done` event (or an SSE extension). The report explains why plain `timings.waiting` is not used.
- [ ] `loadtest/questions.json` holds at least 50 varied questions, so the exact-match cache does not dominate.
- [ ] The stack runs with `LLM_PROVIDER=mock`, `MOCK_TTFT_MS=800`, `MOCK_TOKENS_PER_SEC=60` from a compose override file.
- [ ] Two runs are recorded: cache **off** and cache **on**.
- [ ] A **stress run** ramps past the target until a threshold breaks. The report gives the rate where it broke.
- [ ] `loadtest/RESULTS.md` follows the template below and names a bottleneck with evidence (trace spans, container stats, or logs).
- [ ] A `make loadtest` (or `just`/script) target runs everything with one command.

</AcceptanceCriteria>

## Hints

<Hints>
  <Hint>Start with a smoke run: `RATE=1` for 30 seconds. Confirm that every request parses a `done` event and that `ttft_ms` is close to 800 ms. If TTFT is much higher at 1 request per second, you have overhead before the LLM call (retrieval, re-ranking, an embedding call) that you should measure first.</Hint>
  <Hint>Thresholds are an object keyed by metric name. Use the long form for abort: `sse_error_rate: [{ threshold: 'rate<0.01', abortOnFail: true, delayAbortEval: '30s' }]`. The delay stops one early failure during warm-up from killing the run.</Hint>
  <Hint>For the stress run, switch to `ramping-arrival-rate` with stages like 10, 20, 40, 60 requests per second, two minutes each. Watch `docker stats` and your tracing UI side by side. Note the stage where p95 TTFT crosses 1500 ms. If k6 warns about insufficient VUs, raise `maxVUs`. That warning means k6 itself became the bottleneck.</Hint>
  <Hint>Typical first bottlenecks with the mock: the Postgres pool (look for time spent waiting on pool acquire, or `QueuePool limit` errors), a CPU-bound cross-encoder re-ranker running on the event loop (CPU pinned at 100%, TTFT rises for every request), or a sync Redis client. Find which span grows with load. That span is your answer.</Hint>
</Hints>
