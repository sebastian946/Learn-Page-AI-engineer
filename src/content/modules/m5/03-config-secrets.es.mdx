## Por qué la configuración se complica en apps LLM

Un servicio web clásico tiene una URL de base de datos y algunos toggles. Un servicio LLM tiene mucha más configuración, y gran parte cambia el comportamiento de formas que los tests no detectan:

- API keys de proveedores (Anthropic, OpenAI, Cohere, credenciales de Bedrock).
- Ids de modelo para el modelo principal y el de fallback.
- `max_tokens`, effort (o temperatura, en proveedores que todavía la aceptan), timeouts, cantidad de reintentos.
- Parámetros de retrieval: `top_k`, re-ranker activado o no, umbral de similitud.
- Versión del prompt, TTLs de caché, cuotas de rate limit por tenant.
- Endpoints de base de datos, Redis y tracing.

Dos reglas mantienen esto bajo control:

1. **La configuración es tipada y se valida al arrancar.** Un error de tipeo en `LLM_TIMEOUT_S` debe tumbar el contenedor al iniciar, no producir un 500 a las 2 a.m.
2. **Los secretos nunca viven en el código, en las imágenes ni en git.** La plataforma los inyecta en runtime, y se ocultan en logs y traces.

## pydantic-settings: una sola fuente de verdad tipada

`pydantic-settings` lee variables de entorno (y opcionalmente un archivo `.env` en desarrollo) y las carga en un modelo de Pydantic v2. Obtienes conversión de tipos, validación y valores por defecto en un solo lugar.

```python
# app/settings.py
from functools import lru_cache
from typing import Literal

from pydantic import Field, PostgresDsn, RedisDsn, SecretStr, model_validator
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",          # dev only; missing file is fine
        env_file_encoding="utf-8",
        extra="ignore",
    )

    env: Literal["local", "ci", "staging", "prod"] = "local"
    llm_provider: Literal["anthropic", "mock"] = "anthropic"
    anthropic_api_key: SecretStr | None = None

    primary_model: str = "claude-sonnet-5-5"
    fallback_model: str = "claude-haiku-5-5"
    max_output_tokens: int = Field(default=800, ge=64, le=4096)
    llm_timeout_s: float = Field(default=25.0, gt=0, le=120)
    mock_token_delay_ms: int = Field(default=20, ge=0)

    database_url: PostgresDsn
    redis_url: RedisDsn = RedisDsn("redis://localhost:6379/0")
    db_pool_max: int = Field(default=10, ge=1, le=100)

    prompt_version: str = "answer-v3"
    cache_ttl_s: int = 3600

    @model_validator(mode="after")
    def check_provider_key(self) -> "Settings":
        if self.llm_provider == "anthropic" and self.anthropic_api_key is None:
            raise ValueError("ANTHROPIC_API_KEY is required when LLM_PROVIDER=anthropic")
        if self.env == "prod" and self.llm_provider == "mock":
            raise ValueError("mock provider is not allowed in prod")
        return self


@lru_cache
def get_settings() -> Settings:
    return Settings()
```

Notas:

- **`SecretStr`** se imprime como `**********` en `repr`, logs y tracebacks. Debes llamar a `.get_secret_value()` para leerlo, lo que hace visibles las fugas accidentales en el code review.
- **Los nombres de campo se mapean a variables de entorno** sin distinguir mayúsculas: `database_url` lee `DATABASE_URL`. Usa `env_prefix="MKA_"` si compartes el host con otros servicios.
- **La validación entre campos** detecta combinaciones peligrosas, como el proveedor mock en prod.
- **`lru_cache`** hace que la configuración se parsee una sola vez. En tests, sobrescríbela con dependency overrides de FastAPI o llama a `get_settings.cache_clear()` después de definir variables con `monkeypatch`.
- **`env_file` es una comodidad de desarrollo.** En contenedores, la plataforma define variables de entorno reales, que tienen prioridad sobre el archivo. El `.env` debe estar en `.gitignore` y `.dockerignore`. En su lugar, versiona un `.env.example` con valores falsos.

Falla rápido al arrancar. En `lifespan`, llama primero a `get_settings()`. Si la validación falla, el proceso termina con un error claro y el orquestador marca el deploy como fallido antes de que reciba tráfico. Eso es justo lo que quieres: una configuración incorrecta nunca debe llegar a los usuarios.

## Configuración vs secretos vs prompts

No toda la configuración merece el mismo tratamiento:

| Tipo | Ejemplos | Dónde vive |
|---|---|---|
| Configuración no secreta | ids de modelo, timeouts, `top_k` | Variables de entorno en la task definition, o SSM Parameter Store `String` |
| Secretos | API keys, contraseña de la DB | AWS Secrets Manager o SSM `SecureString`, inyectados en runtime |
| Comportamiento que cambia rápido | versión del prompt, porcentaje de rollout | Servicio de feature flags o tabla de configuración (lección 14) |

Cambiar un id de modelo es un cambio de comportamiento. Debe pasar por la misma revisión y el mismo eval gate que el código. Mantenerlo en configuración versionada (task definition en IaC, o un parámetro con historial de cambios) te da un registro de auditoría.

## Secretos en AWS: inyecta, no consultes (por lo general)

Dos servicios de AWS guardan secretos:

- **Secrets Manager.** Hecho para secretos: soporte de rotación (nativo para RDS), compartir entre cuentas, versionado. Se cobra por secreto al mes más las llamadas a la API.
- **SSM Parameter Store.** Parámetros jerárquicos (`/mka/prod/database_url`). Los valores `SecureString` se cifran con KMS. Los parámetros estándar no tienen costo de almacenamiento. No trae rotación integrada.

Un valor por defecto razonable: credenciales de la DB y API keys de proveedores en Secrets Manager; configuración no secreta en Parameter Store o en variables de entorno simples.

### Opción A: ECS inyecta los secretos como variables de entorno (recomendado)

ECS puede resolver secretos al iniciar la tarea y exponerlos como variables de entorno. Tu código solo lee variables de entorno a través de pydantic-settings y nunca importa boto3 para la configuración.

```json
{
  "containerDefinitions": [
    {
      "name": "api",
      "image": "123456789012.dkr.ecr.us-east-1.amazonaws.com/mka:3f9c2e1",
      "environment": [
        { "name": "ENV", "value": "prod" },
        { "name": "PRIMARY_MODEL", "value": "claude-sonnet-5-5" }
      ],
      "secrets": [
        {
          "name": "ANTHROPIC_API_KEY",
          "valueFrom": "arn:aws:secretsmanager:us-east-1:123456789012:secret:mka/prod/anthropic-AbCdEf"
        },
        {
          "name": "DATABASE_URL",
          "valueFrom": "arn:aws:ssm:us-east-1:123456789012:parameter/mka/prod/database_url"
        }
      ]
    }
  ]
}
```

El **task execution role** necesita `secretsmanager:GetSecretValue` y `ssm:GetParameters` exactamente sobre esos ARNs (más `kms:Decrypt` si usas una key gestionada por el cliente). El **task role** (con el que corre tu código) no los necesita en absoluto. Mínimo privilegio por diseño.

Trade-off: los valores se leen al iniciar la tarea. Después de rotar una key, debes reiniciar las tareas (forzar un nuevo deployment) para que la tomen.

### Opción B: consultar en runtime con caché

Si necesitas rotación sin reinicios, o muchos secretos por tenant, consulta Secrets Manager desde el código y cachea con un TTL:

```python
import json
import time

import boto3

_cache: dict[str, tuple[float, dict]] = {}
_client = boto3.client("secretsmanager")


def get_secret(secret_id: str, ttl_s: int = 300) -> dict:
    now = time.monotonic()
    hit = _cache.get(secret_id)
    if hit and now - hit[0] < ttl_s:
        return hit[1]
    value = json.loads(_client.get_secret_value(SecretId=secret_id)["SecretString"])
    _cache[secret_id] = (now, value)
    return value
```

Es una llamada síncrona; llámala al arrancar o en un threadpool, no en cada request dentro del event loop. AWS también ofrece una librería cliente con caché y un agente sidecar de Secrets Manager para lo mismo. Las API keys por tenant (clientes que traen su propia key del proveedor) son una razón común para necesitar este patrón.

## Nunca en imágenes, nunca en logs

Lugares por donde se filtran secretos en apps LLM:

- **`ENV` o `ARG` de Docker.** Visibles en `docker history` y `docker inspect`. Cualquiera que pueda hacer pull de la imagen puede leerlos.
- **`COPY . .` con un `.env`.** El archivo queda en una capa para siempre, aunque una capa posterior lo borre.
- **Logs de CI.** `echo $ANTHROPIC_API_KEY` para depurar. GitHub enmascara los secretos registrados, pero no los valores derivados de ellos.
- **Traces y prompts.** Las herramientas de tracing capturan headers completos y entradas del prompt. Si un usuario pega una contraseña en el chat, o tu código pone un token en un prompt, termina en tu proveedor de observabilidad. Configura la redacción de datos sensibles.
- **Mensajes de excepción.** Un error de conexión que imprime el DSN completo con contraseña.

Para secretos de build (el token de un índice privado de paquetes), usa secret mounts de BuildKit. El secreto solo está disponible durante ese `RUN` y no se guarda en ninguna capa:

```dockerfile
RUN --mount=type=secret,id=pypi_token,env=UV_INDEX_PRIVATE_PASSWORD \
    uv sync --frozen --no-dev
```

```bash
docker build --secret id=pypi_token,env=PYPI_TOKEN -t mka:dev .
```

En CI, agrega escaneo de secretos (push protection de GitHub, gitleaks) para bloquear una key commiteada antes del merge. Si aun así se filtra una key: primero revócala en el proveedor, luego rótala y después limpia el historial. Asume que fue usada.

## Desarrollo local sin keys reales

Haz que el camino por defecto del desarrollador no necesite secretos de producción:

```bash
# .env.example (committed)
ENV=local
LLM_PROVIDER=mock
DATABASE_URL=postgresql://mka:mka@localhost:5432/mka
REDIS_URL=redis://localhost:6379/0
# ANTHROPIC_API_KEY=sk-ant-...  set your own personal dev key if you need real answers
```

Con `LLM_PROVIDER=mock`, los tests, docker-compose y las pruebas de carga corren con costo cero y cero secretos. Los desarrolladores que necesitan respuestas reales usan su propia key de desarrollo con permisos acotados y un límite de gasto bajo configurado en la consola del proveedor.

## Errores comunes

- **Leer `os.environ` por todo el código.** Sin validación, sin tipos, sin un único lugar para ver qué necesita el servicio. Centraliza en `Settings`.
- **Valores por defecto que solo son seguros en dev.** Por ejemplo, poner `mock` como valor por defecto de `llm_provider` y olvidar sobrescribirlo en prod, o una URL de DB por defecto apuntando a localhost. Prefiere campos obligatorios para todo lo que depende del ambiente.
- **Usar `str` para secretos.** Un `logger.info(settings)` vuelca todas las keys. Usa `SecretStr`.
- **Darle al task role un `secretsmanager:*` amplio.** Limítalo a ARNs exactos y usa el execution role para la inyección.
- **Olvidar que los secretos inyectados se leen una vez.** Rotar una key sin redesplegar deja tareas viejas con una key revocada y provoca una ola de 401.
- **Keys compartidas entre ambientes.** Las pruebas de carga de staging terminan consumiendo los rate limits y el presupuesto de prod. Usa keys de proveedor (o workspaces) separadas por ambiente, con límites de gasto separados.

<Callout type="tip" title="El ángulo SDET">
Escribe tests para la configuración misma: los valores inválidos fallan la validación, prod rechaza el proveedor mock y `repr(Settings(...))` nunca contiene la key en crudo. Son unit tests baratos que previenen incidentes caros.
</Callout>

## Cómo aparece esto en entrevistas

<InterviewQuestion question="¿Cómo gestionas los secretos de un servicio LLM que corre en ECS?" level="mid">
Guarda las keys del proveedor y las credenciales de la DB en AWS Secrets Manager (o SSM `SecureString`). Referéncialos en el bloque `secrets` de la task definition para que ECS los inyecte como variables de entorno al iniciar la tarea. Otorga solo al task execution role `GetSecretValue` sobre esos ARNs específicos. La app lee las variables de entorno con pydantic-settings y `SecretStr`, así que los valores se validan al arrancar y se enmascaran en los logs. Nada secreto va en la imagen, en build args ni en git; `.env` está en `.gitignore` y `.dockerignore`. Rotar significa actualizar el secreto y forzar un nuevo deployment, o consultarlo en runtime con caché TTL si necesitas rotación sin reinicios.
</InterviewQuestion>

<InterviewQuestion question="Alguien subió una API key de Anthropic a un repo público. ¿Qué haces?" level="senior">
Trátala como comprometida de inmediato. Primero revoca la key en la consola del proveedor, no solo borres el commit: hay bots que escanean repos públicos en minutos. Emite una key nueva, guárdala en Secrets Manager y fuerza un redeploy para que las tareas la tomen. Revisa el uso y la facturación en busca de gasto inesperado desde el push. Luego limpia: elimínala del historial si la política lo exige y agrega prevención (push protection o gitleaks en CI, hooks de pre-commit, patrones de `.env` ignorados). Por último, escribe un postmortem breve sin culpables y verifica si la key tenía un alcance mayor al necesario, por ejemplo una sola key compartida por todos los ambientes.
</InterviewQuestion>
