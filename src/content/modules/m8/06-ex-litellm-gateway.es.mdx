## Objetivo

Levanta un pequeño AI gateway en tu laptop y demuestra tres políticas con tests automatizados:

1. **Fallback:** cuando el proveedor principal falla, los requests igual funcionan a través del de respaldo.
2. **Control de acceso:** un equipo solo puede usar los alias de modelo que se le otorgaron.
3. **Presupuestos:** un equipo que gasta su presupuesto es rechazado hasta que el período se reinicia.

Vas a correr el proxy LiteLLM, Postgres y Redis en docker-compose. Para que las fallas sean reproducibles y gratis, los "proveedores" son dos copias de un pequeño servidor mock que habla el formato de chat completions de OpenAI y al que se le puede indicar que falle. Un tercer modelo opcional apunta a la API real de Anthropic si defines `ANTHROPIC_API_KEY`.

Piénsalo como contract testing de infraestructura: la configuración del gateway es el sistema bajo prueba, y pytest es el cliente.

<AcceptanceCriteria>

- [ ] `docker compose up` levanta `litellm`, `postgres`, `redis`, `mock-primary` y `mock-backup`, y el endpoint de health del proxy responde healthy
- [ ] `config.yaml` define los alias `chat-default` (mock-primary), `chat-backup` (mock-backup) y un fallback de `chat-default` a `chat-backup`; las keys de proveedor y la master key vienen solo de variables de entorno
- [ ] Un script de setup crea dos equipos con la API de administración: `team-a` (permitidos: `chat-default`, `chat-backup`; presupuesto pequeño) y `team-b` (permitido: solo `chat-backup`), y una key por equipo
- [ ] Test: con mock-primary sano, un request de `team-a` lo atiende mock-primary (verificado con los contadores `/stats` de los mocks)
- [ ] Test: después de poner mock-primary en modo falla, el mismo request funciona y el contador de mock-backup aumenta
- [ ] Test: un request de `team-b` a `chat-default` es rechazado con un status 4xx
- [ ] Test: los requests de `team-a` son rechazados cuando se agota su presupuesto (el precio del mock es lo bastante alto para alcanzarlo en unos 20 requests)
- [ ] El README muestra el reporte de gasto del equipo obtenido de la API del gateway después de correr los tests

</AcceptanceCriteria>

```python
# mock/server.py — OpenAI-compatible mock provider (pip install fastapi uvicorn)
import os
import time
import uuid

from fastapi import FastAPI, HTTPException

app = FastAPI()
NAME = os.getenv("MOCK_NAME", "mock")
state = {"fail": False, "requests": 0}

@app.post("/v1/chat/completions")
async def chat(body: dict) -> dict:
    state["requests"] += 1
    if state["fail"]:
        raise HTTPException(status_code=503, detail=f"{NAME} unavailable")
    return {
        "id": f"chatcmpl-{uuid.uuid4().hex[:12]}",
        "object": "chat.completion",
        "created": int(time.time()),
        "model": body.get("model", NAME),
        "choices": [{"index": 0, "finish_reason": "stop",
                     "message": {"role": "assistant", "content": f"answer from {NAME}"}}],
        "usage": {"prompt_tokens": 1000, "completion_tokens": 500, "total_tokens": 1500},
    }

@app.post("/admin/fail")
async def set_fail(on: bool) -> dict:
    state["fail"] = on
    return state

@app.get("/stats")
async def stats() -> dict:
    return state
```

```python
import httpx
import pytest

GATEWAY = "http://localhost:4000"

def chat(key: str, model: str) -> httpx.Response:
    return httpx.post(f"{GATEWAY}/v1/chat/completions", timeout=30,
                      headers={"Authorization": f"Bearer {key}"},
                      json={"model": model, "messages": [{"role": "user", "content": "hi"}]})

def requests_seen(port: int) -> int:
    return httpx.get(f"http://localhost:{port}/stats").json()["requests"]

def test_fallback_to_backup(team_a_key: str) -> None:
```

## Pistas

<Hints>
  <Hint>Apunta cada alias a un mock con `model: openai/mock-primary` y `api_base: http://mock-primary:8000/v1` más una `api_key` ficticia. El prefijo `openai/` le dice a LiteLLM que use el formato de OpenAI contra tu base URL. Agrega `input_cost_per_token` y `output_cost_per_token` a `litellm_params` para que el gasto no sea cero con un modelo falso.</Hint>
  <Hint>Haz la cuenta para el test de presupuesto. Con 1.000 tokens de prompt y 500 de completion por respuesta del mock, `input_cost_per_token: 0.00001` y `output_cost_per_token: 0.00002` cuestan 0,02 por request. Un `max_budget` de equipo de 0,4 se agota en unos 20 requests.</Hint>
  <Hint>El gasto se escribe en la base de datos de forma asíncrona y los chequeos de presupuesto pueden ir un poco atrasados. En el test de presupuesto, itera hasta recibir un rechazo (con un tope, por ejemplo 60 requests) en lugar de afirmar que el request número 21 falla exactamente. Los reintentos también cuentan: pon `num_retries: 0` en el alias del test de fallback o tenlo en cuenta al leer los contadores.</Hint>
  <Hint>Pon la creación de equipos y keys en un fixture de pytest con scope de sesión que llame a `/team/new` y `/key/generate` con la master key y devuelva las keys generadas. Para el reporte, `GET /team/info?team_id=...` devuelve el gasto actual del equipo; guarda su JSON en `results/spend.json` y cítalo en el README.</Hint>
