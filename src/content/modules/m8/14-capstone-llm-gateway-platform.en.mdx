## Company context

Harborview Health Plan is a fictional regional health insurer with about 600,000 members and 2,400 employees. Over the last year, four internal teams shipped LLM features on their own:

- **Claims Operations** summarizes claim files and supporting documents for adjusters. The files contain protected health information (PHI): names, member ids, diagnosis codes, provider notes.
- **Member Services** runs an assistant that drafts replies to member emails. Emails often contain PHI.
- **Marketing** generates campaign copy variants. No member data.
- **Engineering Productivity** uses LLMs for internal code review summaries and documentation search. Internal data only.

Each team holds its own provider keys. Spend is visible only on the monthly invoice. Last quarter, a provider outage took down the member reply assistant for three hours, and an internal audit found that one prototype had sent member emails to a public API outside the approved vendor list. The Chief Information Security Officer froze new AI launches until there is a platform.

You are the AI platform engineer hired to build it.

## Business goal

Lift the AI launch freeze by delivering a **shared LLM platform** that every team uses through one gateway, where PHI workloads run only on a self-hosted model inside Harborview's network, every model or prompt change rolls out progressively with automatic rollback, and each team has a budget.

Success in one sentence: "Any team can ship an LLM feature in a week, and the CISO can prove where every request went."

## Functional requirements

1. **AI gateway** (LiteLLM proxy or equivalent) as the single entry point for all four teams, with an OpenAI-compatible API.
2. **Model aliases by data classification:**
   - `phi-chat`: self-hosted open-weight model on vLLM inside the cluster. Only alias allowed for PHI.
   - `general-chat` and `general-fast`: API provider models (for example `claude-sonnet-5-5` and `claude-haiku-5-5` directly or through Bedrock), with fallback across two providers or regions.
3. **Teams and keys:** one gateway team per internal team with an allow-list of aliases, a monthly budget, RPM/TPM limits, and at least one key per service. Claims and Member Services may use `phi-chat` only for PHI traffic; Marketing and Engineering Productivity may not use `phi-chat`.
4. **Compliance-aware routing:** no fallback chain from `phi-chat` leads outside the cluster. When the self-hosted model is unavailable, PHI requests queue or fail clearly.
5. **PII safeguard on general aliases:** a pre-call guardrail that detects and masks PHI patterns on `general-*` aliases, with an alert when it triggers (it indicates a misrouted workload).
6. **Canary releases** for the gateway config, the vLLM model deployment and at least one team's prompt: Argo Rollouts (or ECS canary) gated on error rate, contract validity and p95 TTFT, with automatic rollback.
7. **Release manifests** for the claims summarizer: prompt version, model digest, parameters, guardrail version, eval dataset version and report.
8. **Infrastructure as code:** Terraform for the cloud pieces (network endpoints, IAM, secrets containers, storage for logs), tested with plan-only tests.
9. **Dashboards:** spend per team, requests and errors per alias, p95 TTFT per alias, guardrail triggers, vLLM queue depth and KV cache usage, canary status.
10. **DR plan and rollback runbook**, with at least one rehearsed failover and one rehearsed rollback.

## Non-functional requirements

| Area | Target |
|---|---|
| Latency | p95 time to first token under 2.5 s for `phi-chat` at 30 concurrent streams; gateway overhead under 50 ms at p95, measured separately from provider latency |
| Availability | `general-*` aliases survive the loss of one provider with no user-visible errors beyond retries; `phi-chat` survives the loss of one GPU node with degraded throughput |
| Cost | Report cost per 1k requests per alias. Self-hosted cost from GPU hourly price (example figure, state your assumption) divided by measured throughput |
| Quality | Claims summary eval: faithfulness at or above 0.90 and JSON contract validity at or above 99% on the golden set, for the self-hosted model and any quantized variant |
| Security | No provider key outside the gateway; no PHI in application logs; audit record for every request |
| Recovery | Documented RTO and RPO per component; measured RTO for one rehearsed failure |

## Out of scope

- Building the four teams' applications. Use small stub clients or simple scripts per team.
- Fine-tuning. Use an off-the-shelf instruction model.
- Real PHI. Generate synthetic claim files and emails.
- A full SOC 2 or HIPAA assessment. You produce architecture evidence, not a legal opinion.
- Production-grade GPU capacity. A single small GPU, a CPU vLLM build or a mocked OpenAI-compatible server for `phi-chat` is acceptable if you document it.

## How to present this in an interview

Open with the problem, not the tools: "A health insurer froze AI launches after PHI went to an unapproved API and an outage took down a member-facing assistant. I built the platform that lifted the freeze."

Then walk through three decisions and their trade-offs:

1. **Routing by data classification.** PHI goes only to a self-hosted model, and its fallback is a queue, not a public API. You accepted lower availability for PHI workloads in exchange for a guarantee you can test. Show the test that asserts the external provider's counter never moves.
2. **Progressive delivery with LLM-specific gates.** Contract validity and TTFT per version, not just HTTP errors. Show the recorded auto-rollback and say how long the bad version served traffic and to how many requests.
3. **Evidence by construction.** Terraform history, release manifests, gateway audit logs and rehearsed DR timings are the artifacts an auditor asks for. Name them.

Have numbers ready: gateway overhead at p95, the concurrency knee of the self-hosted model, cost per 1k requests per alias with your stated assumptions, and measured RTO. Close with what you would do next: multi-region warm standby for the gateway database, automated model-retirement tracking, and an online judge-score analysis on the claims canary.
