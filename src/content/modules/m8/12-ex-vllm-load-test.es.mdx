## Objetivo

Convierte los números de la lección 3 en tus propias mediciones. Vas a servir un modelo pequeño de pesos abiertos detrás de la API compatible con OpenAI de vLLM, llevarlo de 1 a 32 streams concurrentes y encontrar el **codo**: la concurrencia donde el tiempo al primer token (TTFT) empieza a subir rápido mientras el throughput total deja de crecer. Ese codo es el número que le darías a un autoscaler y a `--max-num-seqs`.

Este ejercicio es opcional porque necesita una GPU o paciencia:

- **Camino GPU (recomendado):** cualquier GPU NVIDIA de 8 GB o más, usando la imagen oficial `vllm/vllm-openai`.
- **Camino CPU:** vLLM tiene un backend para CPU (sigue la guía de instalación para CPU en la documentación de vLLM). Es lento, pero la forma de las curvas igual es instructiva. Si vLLM en CPU no corre en tu máquina, `llama-server` de `llama.cpp` también expone un endpoint compatible con OpenAI; úsalo y anota que sus métricas son distintas.
- **Camino cloud:** una instancia con una GPU pequeña durante una hora (por ejemplo una `g6.xlarge` de AWS; revisa los precios actuales) y apágala al terminar.

Usa un modelo de instrucciones pequeño con licencia permisiva, como `Qwen/Qwen2.5-0.5B-Instruct` o `Qwen/Qwen2.5-1.5B-Instruct`. El objetivo es el método, no el modelo.

¿Por qué no k6 del Módulo 5? k6 es excelente para la latencia a nivel de request, pero medir el TTFT y la latencia entre tokens requiere leer el stream SSE token por token. Un cliente async corto en Python lo hace con precisión.

```python
# loadtest/stream_bench.py — measure TTFT and inter-token latency under concurrency
import asyncio
import json
import os
import random
import statistics
import time
from dataclasses import dataclass

import httpx

URL = "http://localhost:8000/v1/chat/completions"
HEADERS = {"Authorization": f"Bearer {os.environ['VLLM_API_KEY']}"}

@dataclass
class Sample:
    ttft: float
    itl: float          # mean seconds between tokens after the first
    tokens: int
    duration: float

async def one_request(client: httpx.AsyncClient, prompt: str) -> Sample:
    body = {"model": "small", "stream": True, "max_tokens": 256, "temperature": 0.7,
            "messages": [{"role": "user", "content": prompt}]}
    start = time.perf_counter()
    stamps: list[float] = []
    async with client.stream("POST", URL, json=body, headers=HEADERS) as resp:
        resp.raise_for_status()
        async for line in resp.aiter_lines():
            if not line.startswith("data: ") or line == "data: [DONE]":
                continue
            delta = json.loads(line[6:])["choices"][0]["delta"].get("content")
            if delta:
                stamps.append(time.perf_counter())
    end = time.perf_counter()
    gaps = [b - a for a, b in zip(stamps, stamps[1:])]
    return Sample(ttft=stamps[0] - start if stamps else end - start,
                  itl=statistics.mean(gaps) if gaps else 0.0,
                  tokens=len(stamps), duration=end - start)

async def run_level(concurrency: int, prompts: list[str], total: int) -> list[Sample]:
    sem = asyncio.Semaphore(concurrency)
    async with httpx.AsyncClient(timeout=120) as client:
        async def guarded() -> Sample:
            async with sem:
                return await one_request(client, random.choice(prompts))
        return await asyncio.gather(*(guarded() for _ in range(total)))
```

## Pistas

<Hints>
  <Hint>Contar los chunks del stream aproxima los tokens lo suficiente para comparar niveles, pero para números exactos pide el uso dentro del stream (`"stream_options": {"include_usage": true}`), que vLLM soporta, y lee `usage.completion_tokens` del último chunk.</Hint>
  <Hint>El throughput total es la suma de tokens de salida dividida por el tiempo de reloj de todo el nivel, no la suma de las tasas por request. Corre primero un nivel corto de calentamiento y descártalo; los primeros requests después del arranque incluyen la captura de CUDA graphs y el calentamiento de cachés.</Hint>
  <Hint>Para `/metrics`, corre una tarea en segundo plano que consulte cada segundo y parsee las líneas que empiezan con `vllm:num_requests_waiting` y el gauge de uso del KV cache (`vllm:kv_cache_usage_perc`, o `vllm:gpu_cache_usage_perc` en versiones anteriores). Guarda el máximo por nivel. vLLM también registra al arrancar la cantidad de bloques de KV cache; multiplícala por el tamaño de bloque para obtener la capacidad en tokens que realmente reservó.</Hint>
  <Hint>Define el codo de forma concreta, por ejemplo "la menor concurrencia donde el TTFT p95 es más del doble del valor con un usuario, o donde el throughput total crece menos del 10% respecto del nivel anterior". Con una definición, tu recomendación es reproducible en lugar de a ojo.
