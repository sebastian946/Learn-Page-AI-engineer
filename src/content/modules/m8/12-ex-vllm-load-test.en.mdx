## Goal

Turn lesson 3's numbers into your own measurements. You will serve a small open-weight model behind vLLM's OpenAI-compatible API, push it from 1 to 32 concurrent streams, and find the **knee**: the concurrency where time to first token (TTFT) starts climbing fast while total throughput stops growing. That knee is the number you would feed to an autoscaler and to `--max-num-seqs`.

This exercise is optional because it needs either a GPU or patience:

- **GPU path (recommended):** any single NVIDIA GPU with 8 GB or more, using the official `vllm/vllm-openai` image.
- **CPU path:** vLLM has a CPU backend (follow the CPU installation guide in the vLLM docs). It is slow, but the curve shapes are still instructive. If vLLM CPU will not run on your machine, `llama.cpp`'s `llama-server` also exposes an OpenAI-compatible endpoint; use it and note that its metrics differ.
- **Cloud path:** a single small GPU instance for an hour (for example an AWS `g6.xlarge`; check current pricing) and shut it down afterwards.

Use a small instruction model with a permissive license, such as `Qwen/Qwen2.5-0.5B-Instruct` or `Qwen/Qwen2.5-1.5B-Instruct`. The goal is the method, not the model.

Why not k6 from Module 5? k6 is great for request-level latency, but measuring TTFT and inter-token latency needs reading the SSE stream token by token. A short async Python client does that precisely.

```python
# loadtest/stream_bench.py — measure TTFT and inter-token latency under concurrency
import asyncio
import json
import os
import random
import statistics
import time
from dataclasses import dataclass

import httpx

URL = "http://localhost:8000/v1/chat/completions"
HEADERS = {"Authorization": f"Bearer {os.environ['VLLM_API_KEY']}"}

@dataclass
class Sample:
    ttft: float
    itl: float          # mean seconds between tokens after the first
    tokens: int
    duration: float

async def one_request(client: httpx.AsyncClient, prompt: str) -> Sample:
    body = {"model": "small", "stream": True, "max_tokens": 256, "temperature": 0.7,
            "messages": [{"role": "user", "content": prompt}]}
    start = time.perf_counter()
    stamps: list[float] = []
    async with client.stream("POST", URL, json=body, headers=HEADERS) as resp:
        resp.raise_for_status()
        async for line in resp.aiter_lines():
            if not line.startswith("data: ") or line == "data: [DONE]":
                continue
            delta = json.loads(line[6:])["choices"][0]["delta"].get("content")
            if delta:
                stamps.append(time.perf_counter())
    end = time.perf_counter()
    gaps = [b - a for a, b in zip(stamps, stamps[1:])]
    return Sample(ttft=stamps[0] - start if stamps else end - start,
                  itl=statistics.mean(gaps) if gaps else 0.0,
                  tokens=len(stamps), duration=end - start)

async def run_level(concurrency: int, prompts: list[str], total: int) -> list[Sample]:
    sem = asyncio.Semaphore(concurrency)
    async with httpx.AsyncClient(timeout=120) as client:
        async def guarded() -> Sample:
            async with sem:
                return await one_request(client, random.choice(prompts))
        return await asyncio.gather(*(guarded() for _ in range(total)))
```

## Hints

<Hints>
  <Hint>Counting streamed chunks approximates tokens well enough for comparisons across levels, but for exact numbers request usage in the stream (`"stream_options": {"include_usage": true}`), which vLLM supports, and read the final chunk's `usage.completion_tokens`.</Hint>
  <Hint>Total throughput is total output tokens divided by the wall-clock time of the whole level, not the sum of per-request rates. Run a short warm-up level first and discard it; the first requests after startup include CUDA graph capture and cache warm-up.</Hint>
  <Hint>For `/metrics`, run a background task that fetches every second and parses lines starting with `vllm:num_requests_waiting` and the KV cache usage gauge (`vllm:kv_cache_usage_perc`, or `vllm:gpu_cache_usage_perc` on older versions). Keep the max per level. vLLM also logs the number of KV cache blocks at startup; multiply by the block size to get the token capacity it actually allocated.</Hint>
  <Hint>Define the knee concretely, for example "the lowest concurrency where p95 TTFT is more than 2x the single-user value, or where total throughput grows less than 10% from the previous level". With a definition, your recommendation is reproducible instead of eyeballed. Bonus: register the server in your Module 8 gateway as `chat-private` and rerun one level through LiteLLM to measure the gateway's overhead.</Hint>
