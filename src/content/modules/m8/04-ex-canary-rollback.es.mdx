## Objetivo

Demostrar, en tu laptop, que un cambio de prompt malo se revierte solo antes de que lo vea la mayoría de los usuarios.

Vas a correr un pequeño servicio de "triage" en un cluster local de Kubernetes (kind o minikube), gestionarlo con **Argo Rollouts** y controlar el canary con dos señales de Prometheus de la lección 1: tasa de errores y validez del contrato de salida. Luego publicas dos releases:

1. `v2-bad`: un cambio de prompt que rompe el contrato JSON en alrededor del 30% de los requests. Debe abortar automáticamente.
2. `v3`: un cambio bueno. Debe promoverse hasta el 100% sin intervención humana.

El servicio simula la llamada al LLM por defecto, así que no necesitas API key y la ejecución es reproducible. Un switch `REAL_LLM=1` te permite llamar a `claude-haiku-5-5` si quieres probar con salidas reales.

Esta es la versión de progressive delivery del eval gate que construiste en el Módulo 3: CI revisa el cambio antes del merge, el canary lo vuelve a revisar con tráfico real.

<AcceptanceCriteria>

- [ ] Un cluster kind (o minikube) corre el controlador de Argo Rollouts y Prometheus (el chart `prometheus-community/prometheus` alcanza)
- [ ] El servicio expone `llm_requests_total{status}` y `llm_contract_checks_total{result}` en `/metrics`, y Prometheus agrega una etiqueta `version` (`canary` o `stable`) desde las etiquetas del pod
- [ ] Un `Rollout` con 4 réplicas usa pasos canary: 25% → análisis → 50% → pausa de 2 minutos → 100%
- [ ] Un `AnalysisTemplate` verifica tasa de errores menor al 2% y validez del contrato mayor o igual al 98%, y trata "todavía no hay datos" como no fallido, no como aprobado
- [ ] Un generador de carga envía tráfico constante (unos 10 requests por segundo) a través del Service durante cada rollout
- [ ] Desplegar `v2-bad` termina con el Rollout en `Degraded`, los pods canary en 0 y el 100% del tráfico en estable, sin ningún comando manual
- [ ] Desplegar `v3` llega a `Healthy` al 100% sin promote manual
- [ ] El README registra, para el release malo, el tiempo desde el deploy hasta el abort automático y la cantidad aproximada de requests que atendió la versión mala

</AcceptanceCriteria>

```python
# app/main.py — fake LLM triage service (pip install fastapi uvicorn prometheus-client)
import json
import os
import random

from fastapi import FastAPI
from prometheus_client import Counter, make_asgi_app
from pydantic import BaseModel, ValidationError

PROMPT_VERSION = os.getenv("PROMPT_VERSION", "v1")
FAULT_RATE = float(os.getenv("FAULT_RATE", "0.0"))      # share of broken outputs
ERROR_RATE = float(os.getenv("ERROR_RATE", "0.0"))      # share of upstream failures

REQUESTS = Counter("llm_requests_total", "LLM requests", ["status"])
CONTRACT = Counter("llm_contract_checks_total", "Output contract checks", ["result"])

app = FastAPI()
app.mount("/metrics", make_asgi_app())

class Ticket(BaseModel):
    text: str

class Triage(BaseModel):
    category: str
    priority: int
    reply: str

def fake_llm(ticket: Ticket) -> str:
    if random.random() < FAULT_RATE:
        return "Sure! Here is the triage: category billing, priority 2"  # not JSON
    return json.dumps({"category": "billing", "priority": 2,
                       "reply": f"[{PROMPT_VERSION}] We are looking into it."})

@app.post("/triage")
async def triage(ticket: Ticket) -> dict:
    if random.random() < ERROR_RATE:
        REQUESTS.labels("error").inc()
        return {"error": "upstream_unavailable"}
    raw = fake_llm(ticket)  # TODO: if REAL_LLM=1, call claude-haiku-5-5 instead
    try:
        result = Triage.model_validate_json(raw)
    except ValidationError:
        CONTRACT.labels("invalid").inc()
        REQUESTS.labels("ok").inc()
        return {"fallback": True}
    CONTRACT.labels("valid").inc()
    REQUESTS.labels("ok").inc()
    return result.model_dump()

@app.get("/healthz")
async def healthz() -> dict:
    return {"ok": True}
```

```python
# scripts/loadgen.py — steady traffic through a port-forwarded Service
import asyncio
import httpx

async def main(rps: int = 10, url: str = "http://localhost:8080/triage") -> None:
    async with httpx.AsyncClient(timeout=10) as client:
        while True:
            tasks = [client.post(url, json={"text": "I was charged twice"}) for _ in range(rps)]
            await asyncio.gather(*tasks, return_exceptions=True)
            await asyncio.sleep(1)

if __name__ == "__main__":
    asyncio.run(main())
```

## Pistas

<Hints>
  <Hint>Orden de instalación: `kind create cluster`, luego el controlador de Argo Rollouts (`kubectl create namespace argo-rollouts` y aplica el `install.yaml` de los releases del proyecto), luego el plugin de kubectl, y luego `helm install prometheus prometheus-community/prometheus -n monitoring --create-namespace`. Construye la imagen y cárgala en kind con `kind load docker-image triage:v1` para no necesitar registry.</Hint>
  <Hint>El job de scrape `kubernetes-pods` por defecto del chart respeta las anotaciones `prometheus.io/*` y tiene una regla `labelmap` para las etiquetas del pod, así que `version` aparece en tus series sin esfuerzo. Verifícalo en la UI de Prometheus (`kubectl port-forward svc/prometheus-server -n monitoring 9090:80`) con `sum by (version) (rate(llm_requests_total[1m]))` antes de escribir el análisis.</Hint>
  <Hint>Justo cuando empieza un paso, el canary puede no tener muestras y el cociente queda vacío o NaN. Usa `count` e `interval` para que el análisis tome varias mediciones, pon `failureLimit: 1` y escribe la condición a la defensiva, por ejemplo `successCondition: len(result) == 0 || isNaN(result[0]) || result[0] >= 0.98`, combinada con una métrica aparte que falle si el canary atendió menos de una cantidad mínima de requests en la ventana. Así "sin datos" no puede aprobar el paso entero en silencio.</Hint>
  <Hint>Para publicar un release, cambia el template del pod: `kubectl argo rollouts set image triage api=triage:v2` más el cambio de env, o edita `rollout.yaml` (`PROMPT_VERSION: v2-bad`, `FAULT_RATE: "0.3"`) y haz `kubectl apply`. Obsérvalo con `kubectl argo rollouts get rollout triage --watch`. Después de un abort, el Rollout queda en `Degraded` hasta que apliques una revisión nueva o corras `kubectl argo rollouts undo triage`; es lo esperado y es tu señal para investigar.</Hint>
</Hints>
