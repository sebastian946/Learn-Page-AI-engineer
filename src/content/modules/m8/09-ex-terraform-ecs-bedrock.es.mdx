## Objetivo

Escribe un módulo de Terraform reutilizable, `llm-ecs-service`, que despliegue una API LLM en ECS Fargate como describió la lección 7, y **demuestra sus propiedades de seguridad con tests que corren sin cuenta de AWS**.

El módulo debe crear:

- una task definition y un servicio de ECS en subredes privadas sin IP pública;
- un ALB y un target group con timeouts adecuados para streaming;
- un interface VPC endpoint para `bedrock-runtime` con una política de endpoint;
- roles IAM de ejecución y de task con mínimo privilegio;
- una referencia a la API key del proveedor en Secrets Manager (el valor nunca en el código ni en el state).

Lo vas a probar con `terraform test` y un **provider de AWS mockeado** (Terraform 1.7 o más nuevo). Los providers mockeados devuelven valores falsos para los atributos calculados, así que `command = plan` corre offline y tus aserciones verifican la lógica de la configuración. Si tienes una cuenta sandbox de AWS, un `terraform plan` real es un extra, no un requisito.

El enfoque de SDET: esto es unit testing de infraestructura. Cada aserción codifica un requisito que, si no, un revisor de seguridad verificaría a mano.

<AcceptanceCriteria>

- [ ] `terraform fmt -check` y `terraform validate` pasan para el módulo y para la raíz de ejemplo
- [ ] El módulo expone variables tipadas con descripciones, incluidas `allowed_model_arns`, `idle_timeout_seconds` (validada en 120 o más) y `drain_seconds`
- [ ] `terraform test` pasa con `mock_provider "aws"` y al menos 6 bloques `run`
- [ ] Un test afirma que el idle timeout del ALB es de al menos 120 segundos y que el deregistration delay del target group es igual a `drain_seconds`
- [ ] Un test usa `expect_failures` para demostrar que `idle_timeout_seconds = 60` es rechazado
- [ ] Un test afirma que el endpoint de bedrock-runtime usa el nombre de servicio regional correcto, tiene DNS privado habilitado y que su política lista exactamente `allowed_model_arns`
- [ ] Un test afirma que ninguna sentencia IAM del task role usa `bedrock:*` ni un resource `*`
- [ ] Un test afirma que la definición del contenedor recibe la API key mediante `secrets` (un ARN de Secrets Manager) y que ningún nombre de entrada en `environment` contiene `KEY` o `SECRET`
- [ ] Checkov (o el escaneo de configuración de Trivy) corre sobre el módulo; los hallazgos se corrigen o se omiten con una razón escrita

</AcceptanceCriteria>

## Pistas

<Hints>
  <Hint>Mantén la política IAM como un data source `aws_iam_policy_document` cuyos bloques `statement` se construyen a partir de variables. Los argumentos que defines se conocen en tiempo de plan incluso con un provider mockeado, así que un test puede inspeccionar `data.aws_iam_policy_document.invoke_models.statement` directamente. Solo los atributos calculados como `.json` reciben valores falsos.</Hint>
  <Hint>Si un recurso valida JSON que viene de un data source mockeado (por ejemplo una role policy construida desde `.json`), el string aleatorio del mock puede dar problemas. Usa un bloque `override_data` en el archivo de test para darle a ese data source un valor `json` realista, o construye la política con `jsonencode` en un `local` sobre el que también puedas hacer aserciones.</Hint>
  <Hint>Para el test de comodines de IAM, aplana las acciones y los resources de cada sentencia y verifícalos con `alltrue`, por ejemplo `alltrue([for s in data.aws_iam_policy_document.invoke_models.statement : !contains(s.actions, "bedrock:*")])`, y la misma idea para `"*"` en `resources`. Para el test del contenedor, `jsondecode(aws_ecs_task_definition.api.container_definitions)[0]` te da las listas `secrets` y `environment`.</Hint>
  <Hint>Checkov marcará cosas como que el ALB no tiene access logs o que el target group usa HTTP. Corrige lo barato (access logs hacia un bucket recibido como variable, `drop_invalid_header_fields`), y para el resto agrega skips inline con una razón, como que TLS termina en el ALB dentro de una red privada. A un revisor le importa que cada skip sea una decisión, no que la lista esté vacía.</Hint>
</Hints>
