## Goal

Write a reusable Terraform module, `llm-ecs-service`, that deploys an LLM API on ECS Fargate the way lesson 7 described, and **prove its security properties with tests that run without an AWS account**.

The module must create:

- an ECS task definition and service in private subnets with no public IP;
- an ALB and target group with streaming-friendly timeouts;
- an interface VPC endpoint for `bedrock-runtime` with an endpoint policy;
- execution and task IAM roles with least privilege;
- a reference to a provider API key in Secrets Manager (the value never in code or state).

You will test it with `terraform test` and a **mocked AWS provider** (Terraform 1.7 or newer). Mocked providers return fake values for computed attributes, so `command = plan` runs offline and your assertions check the configuration logic. If you have a sandbox AWS account, a real `terraform plan` is a bonus, not a requirement.

The SDET framing: this is unit testing for infrastructure. Each assertion encodes a requirement a security reviewer would otherwise check by hand.

<AcceptanceCriteria>

- [ ] `terraform fmt -check` and `terraform validate` pass for the module and the example root
- [ ] The module exposes typed variables with descriptions, including `allowed_model_arns`, `idle_timeout_seconds` (validated at 120 or more) and `drain_seconds`
- [ ] `terraform test` passes with `mock_provider "aws"` and at least 6 `run` blocks
- [ ] A test asserts the ALB idle timeout is at least 120 seconds and the target group deregistration delay equals `drain_seconds`
- [ ] A test uses `expect_failures` to prove that `idle_timeout_seconds = 60` is rejected
- [ ] A test asserts the bedrock-runtime endpoint uses the correct regional service name, has private DNS enabled, and its policy lists exactly `allowed_model_arns`
- [ ] A test asserts no IAM statement in the task role uses `bedrock:*` or a `*` resource
- [ ] A test asserts the container definition gets the API key through `secrets` (a Secrets Manager ARN) and that no `environment` entry name contains `KEY` or `SECRET`
- [ ] Checkov (or Trivy config scan) runs on the module; findings are fixed or skipped with a written reason

</AcceptanceCriteria>

## Hints

<Hints>
  <Hint>Keep the IAM policy as an `aws_iam_policy_document` data source whose `statement` blocks are built from variables. Arguments you set are known at plan time even with a mocked provider, so a test can inspect `data.aws_iam_policy_document.invoke_models.statement` directly. Only computed attributes like `.json` get fake values.</Hint>
  <Hint>If a resource validates JSON that comes from a mocked data source (for example a role policy built from `.json`), the mock's random string can cause trouble. Use an `override_data` block in the test file to give that data source a realistic `json` value, or build the policy with `jsonencode` in a `local` that you can also assert on.</Hint>
  <Hint>For the IAM wildcard test, flatten every statement's actions and resources and check them with `alltrue`, for example `alltrue([for s in data.aws_iam_policy_document.invoke_models.statement : !contains(s.actions, "bedrock:*")])`, and the same idea for `"*"` in `resources`. For the container test, `jsondecode(aws_ecs_task_definition.api.container_definitions)[0]` gives you the `secrets` and `environment` lists.</Hint>
  <Hint>Checkov will flag things like the ALB not having access logs or the target group using HTTP. Fix what is cheap (access logs to a bucket variable, `drop_invalid_header_fields`), and for the rest add inline skips with a reason, such as TLS terminating at the ALB inside a private network. A reviewer cares that each skip is a decision, not that the list is empty.</Hint>
</Hints>
