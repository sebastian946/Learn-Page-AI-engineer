## Goal

Run two timed mock system-design interviews on yourself and publish the write-ups in a new repo, `system-design-notes`. This repo becomes a reference you reread before every onsite, and a portfolio signal that you can reason about AI systems at the architecture level.

- **Prompt A (45 min):** "Design a RAG system for 10,000 users." Do it without looking at the previous lesson. Then compare.
- **Prompt B (45 min):** "Design an agent platform for customer support. Agents answer tickets for 50 B2B customers, can look up orders and issue refunds up to a limit, and escalate to humans."

Timebox strictly: set a 45-minute timer per prompt. Stop when it rings, even mid-sentence. Then spend 10 minutes self-grading with the rubric from lesson 04, and 10 minutes writing "what I missed".

Why timed? In a real round, running out of time before covering evals or failure modes costs more than a slightly worse diagram. Your QA instinct for test coverage applies: cover every area shallowly first, then go deep.

For Prompt B, these are the areas a strong answer covers that Prompt A does not:

- **Tool design:** idempotent refund tool with an idempotency key, a per-tenant refund limit enforced in the tool, not in the prompt.
- **Human-in-the-loop:** approval step for refunds above the limit, using LangGraph interrupts and checkpoints.
- **Loop guards and cost caps:** max steps per ticket, max tokens per ticket, and a kill switch per tenant.
- **Trajectory evals:** did the agent call the right tools in the right order with the right arguments, not only "was the final reply good".
- **Multi-tenancy:** each B2B customer has its own knowledge base, tone guide, tool credentials and policies.
- **Escalation:** confidence and sentiment thresholds, plus a clean handoff that includes a summary for the human agent.
- **Audit:** every tool call logged with inputs, outputs and the approving human, if any.

    queries_per_dau: float
    active_hours: float
    peak_factor: float

    out_tokens: int
