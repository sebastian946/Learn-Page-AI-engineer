## De la suite de regresión al gate de evals

Ya sabes cómo funciona una suite de regresión. Cada PR corre los tests. Un build en rojo bloquea el merge. La suite crece cada vez que un bug se escapa.

Las apps con LLM necesitan la misma disciplina. La diferencia está en la aserción. Un unit test verifica `assert total == 42`. Un eval verifica "el faithfulness sobre el golden set es al menos 0.85 y no bajó más de 0.03 respecto a main". Haces aserciones sobre **puntajes agregados con tolerancias**, no sobre strings exactos.

Este es el mapeo:

| Concepto de QA | Equivalente en evals de LLM |
|---|---|
| Suite de regresión | Golden dataset (`evals/datasets/golden_v3.jsonl`) |
| Aserción | Umbral de métrica (absoluto) o delta contra baseline (relativo) |
| Test flaky | Salida no determinista: temperatura, muestreo, cambios del proveedor |
| Retry ante flake | Muestreo repetido + intervalos de confianza |
| Fixtures / mocks | Caché de respuestas con clave por modelo + prompt + parámetros |
| Smoke vs regresión completa | Subconjunto en PR vs suite completa nocturna |
| Test impact analysis | Path filters: correr evals solo cuando cambian prompts o retrieval |
| Presupuesto de minutos de CI | Presupuesto de tokens / dólares por corrida de evals |

¿Qué dispara una regresión? No solo el código. Una edición de prompt, un nuevo tamaño de chunk, otro modelo de embeddings, un cambio de re-ranker, una actualización del modelo del lado del proveedor o un nuevo lote de documentos en el índice. Tu gate debe correr en todos esos casos.

## Dos tipos de umbrales

Los **umbrales absolutos** son requisitos de producto. "El faithfulness debe ser al menos 0.85" porque cumplimiento (compliance) lo pidió. Nunca se mueven sin el acuerdo del product owner.

Los **umbrales relativos** atrapan regresiones. Guardas los últimos puntajes aceptados de `main` en `evals/baseline.json`. Un PR falla si una métrica baja más que una tolerancia.

```json
{
  "dataset": "golden_v3",
  "commit": "a1b2c3d",
  "metrics": {
    "faithfulness": 0.91,
    "answer_relevance": 0.88,
    "citation_accuracy": 0.95,
    "refusal_correctness": 0.97
  },
  "tolerance": { "default": 0.03, "citation_accuracy": 0.02 }
}
```

Usa ambos. Los umbrales absolutos evitan que publiques algo malo. Los relativos evitan la erosión lenta. Sin el chequeo relativo, los puntajes pueden bajar de 0.95 a 0.86 un PR "inofensivo" a la vez sin tocar nunca el piso absoluto.

## Escribir el gate con pytest

Pytest es un buen runner para evals. Tienes markers, fixtures, parametrización, JUnit XML y plugins que ya usas. Deja el trabajo caro (llamar a la app y al juez) en un fixture de sesión. Mantén cada aserción pequeña.

```python
# tests/test_regression.py
import json
from pathlib import Path

import pytest

from harness.runner import EvalRun, run_suite

BASELINE = json.loads(Path("evals/baseline.json").read_text())
FLOORS = {"faithfulness": 0.85, "citation_accuracy": 0.90}


@pytest.fixture(scope="session")
def eval_run(request: pytest.FixtureRequest) -> EvalRun:
    subset = request.config.getoption("--subset")  # "pr" or "full"
    return run_suite(dataset="evals/datasets/golden_v3.jsonl", subset=subset, samples=3)


@pytest.mark.eval
@pytest.mark.parametrize("metric", sorted(BASELINE["metrics"]))
def test_no_regression_vs_baseline(eval_run: EvalRun, metric: str) -> None:
    baseline = BASELINE["metrics"][metric]
    tol = BASELINE["tolerance"].get(metric, BASELINE["tolerance"]["default"])
    score = eval_run.scores[metric]
    assert score.mean >= baseline - tol, (
        f"{metric} regressed: {score.mean:.3f} vs baseline {baseline:.3f} "
        f"(tolerance {tol}, 95% CI {score.ci_low:.3f}-{score.ci_high:.3f})"
    )


@pytest.mark.eval
@pytest.mark.parametrize("metric,floor", sorted(FLOORS.items()))
def test_absolute_floor(eval_run: EvalRun, metric: str, floor: float) -> None:
    assert eval_run.scores[metric].mean >= floor


@pytest.mark.eval
def test_cost_budget(eval_run: EvalRun) -> None:
    assert eval_run.cost_usd <= 2.00, f"eval run cost ${eval_run.cost_usd:.2f}"
```

Registra `--subset` en `conftest.py` con `parser.addoption`, y registra el marker `eval` en `pyproject.toml` para que `pytest -m "not eval"` mantenga rápidos tus unit tests.

Fíjate en el mensaje de falla. Imprime el puntaje, el baseline, la tolerancia y el intervalo de confianza. Un revisor debe entender un build en rojo sin abrir logs. Es la misma regla que aplicas a los mensajes de aserción en Playwright.

## No determinismo: el test flaky que no puedes borrar

Con un test de UI flaky, arreglas la condición de carrera. Con un LLM, la varianza es una característica del sistema. Los modelos actuales de Claude ni siquiera aceptan `temperature`, e incluso en los proveedores que sí lo aceptan, `temperature=0` no impide que las salidas cambien entre corridas por efectos de batching y punto flotante del lado del proveedor. Los jueces agregan su propia varianza.

Tácticas, de la más barata a la más robusta:

1. **Restringe la salida y evalúa con la configuración de producción.** No puedes bajar la temperatura en los modelos actuales de Claude, así que usa structured outputs donde la tarea lo permita y evalúa con el mismo id de modelo y el mismo `effort` que producción, porque eso es lo que ven los usuarios.
2. **Fija el juez.** Model id exacto del juez, versión fija de la rúbrica, veredicto con salida estructurada. Cambiar el juez cambia la regla de medir. Trátalo como un reinicio del baseline.
3. **Muestreo repetido.** Corre cada pregunta `k` veces (3 es un inicio común) y promedia. Esto reduce la varianza aproximadamente en la raíz cuadrada de `k`.
4. **Intervalos de confianza.** Reporta la media con un CI por bootstrap. Si el CI de un PR se superpone mucho con el baseline, la "caída" probablemente es ruido.

```python
# harness/metrics.py
import random
from dataclasses import dataclass
from statistics import mean


@dataclass(frozen=True)
class Score:
    mean: float
    ci_low: float
    ci_high: float
    n: int


def bootstrap_ci(values: list[float], iters: int = 2000, alpha: float = 0.05, seed: int = 7) -> Score:
    rng = random.Random(seed)  # seeded: the CI itself must be reproducible
    n = len(values)
    means = sorted(mean(rng.choices(values, k=n)) for _ in range(iters))
    lo = means[int(alpha / 2 * iters)]
    hi = means[int((1 - alpha / 2) * iters) - 1]
    return Score(mean=mean(values), ci_low=lo, ci_high=hi, n=n)
```

Regla práctica: con 50 preguntas y puntajes binarios, un CI del 95% es de más o menos 0.1 alrededor de 0.8. Es amplio. Así que una tolerancia de 0.03 sobre 50 ítems producirá falsas alarmas. Haz crecer el dataset, muestrea más o amplía la tolerancia para sets pequeños. Sé honesto en el README sobre cuántos ítems respaldan cada gate.

## Caché: fixtures para llamadas a LLM

Re-ejecutar 200 preguntas por 3 muestras por una llamada al juez en cada push quema dinero y minutos. Cachea las respuestas con una clave que incluya todo lo que puede cambiar la salida.

```python
# harness/cache.py
import hashlib
import json
from pathlib import Path
from typing import Any

CACHE_DIR = Path(".eval_cache")


def cache_key(model: str, system: str, messages: list[dict[str, Any]], params: dict[str, Any], sample_idx: int) -> str:
    payload = json.dumps(
        {"model": model, "system": system, "messages": messages, "params": params, "sample": sample_idx},
        sort_keys=True,
    )
    return hashlib.sha256(payload.encode()).hexdigest()


def get(key: str) -> dict[str, Any] | None:
    path = CACHE_DIR / f"{key}.json"
    return json.loads(path.read_text()) if path.exists() else None


def put(key: str, value: dict[str, Any]) -> None:
    CACHE_DIR.mkdir(exist_ok=True)
    (CACHE_DIR / f"{key}.json").write_text(json.dumps(value))
```

Dos cachés, dos propósitos:

- **Caché del juez.** Misma respuesta, misma rúbrica, mismo modelo juez significa el mismo veredicto. Es seguro cachear agresivamente.
- **Caché del sistema bajo prueba.** Solo es válido si el prompt, los contextos recuperados y los parámetros forman parte de la clave. Incluye `sample_idx` para que el muestreo repetido siga produciendo `k` muestras distintas. Si el retrieval cambió, los contextos cambiaron, la clave cambió y obtienes una llamada nueva. Ese es exactamente el comportamiento que quieres.

Los cache hits en preguntas sin cambios hacen que un PR que solo toca un prompt cueste centavos. Agrega un flag `--no-cache` para el job nocturno, así el drift del lado del proveedor sigue apareciendo.

## Control de costos y selección de tests

Trata los tokens como minutos de CI.

- **Path filters.** Corre el workflow de evals solo cuando cambian `prompts/**`, `app/retrieval/**`, `app/generation/**`, `evals/**` o la configuración del modelo. Un typo en el README no debería costar una corrida de evals.
- **Subconjunto en PR vs completo nocturno.** En PRs corre un subconjunto estratificado (por ejemplo 60 ítems que cubran todos los tags). De noche, corre todos los ítems con `samples=3` y sin caché. Semanalmente, agrega la muestra cara de revisión humana.
- **Primero el juez barato.** Usa `claude-haiku-5-5` para chequeos binarios fáciles (¿citó? ¿se negó?) y `claude-sonnet-5-5` para faithfulness.
- **Presupuesto duro.** Registra los tokens por llamada. Aborta la corrida si el costo proyectado supera el presupuesto. Un loop desbocado en un prompt de juez debe fallar rápido, no a fin de mes.
- **Primero los chequeos deterministas.** Validación de esquema, existencia de ids de citas, frases prohibidas y límites de longitud no cuestan nada. Falla rápido en ellos antes de gastar tokens en métricas evaluadas por modelo. Esa es la pirámide de evals en la práctica.

## Errores comunes

- **Aserciones de coincidencia exacta sobre texto libre.** Fallan con cada reformulación. Haz aserciones sobre métricas, esquemas o campos extraídos.
- **Una muestra, tolerancia estrecha.** Construiste un test flaky. Mide primero la varianza entre corridas y luego pon la tolerancia por encima de ella.
- **Cambiar el juez y el prompt en el mismo PR.** No puedes saber cuál movió el puntaje.
- **Baseline actualizado desde la rama del PR.** Los baselines solo deben escribirse desde `main` después del merge, o cualquiera puede bajar la vara haciendo commit de un nuevo baseline.
- **Clave de caché sin los contextos o los parámetros.** Servirás respuestas viejas y tendrás builds en verde con el retrieval roto.
- **Sin visibilidad de costos.** La primera señal del problema es la factura. Imprime el costo por corrida en el resumen del job.
- **Esconder fallas por ítem detrás de un promedio.** Publica siempre los 10 peores ítems. Los promedios esconden la única respuesta que da un consejo equivocado sobre límites de préstamo.

## Cómo aparece esto en entrevistas

<InterviewQuestion question="¿Cómo evitas que un cambio de prompt degrade silenciosamente un sistema RAG?" level="mid">

Trato los prompts como código con una suite de regresión. Mantengo un golden dataset versionado y un gate de evals basado en pytest en CI. Corre cuando cambian los prompts, el código de retrieval o la configuración del modelo. Primero verifica cosas deterministas (esquema, que los ids de citas existan) y luego métricas evaluadas por modelo como faithfulness, con un juez fijo. Cada métrica tiene un piso absoluto que viene del requisito de producto y una tolerancia relativa contra un baseline guardado desde `main`. El PR falla si el faithfulness baja más de 0.03. Cacheo las llamadas al juez para que un PR pequeño cueste centavos, y corro la suite completa cada noche sin caché para detectar drift del proveedor.

</InterviewQuestion>

<InterviewQuestion question="Tu gate de evals falla al azar más o menos una de cada cinco corridas. ¿Qué haces?" level="senior">

Es un test flaky, así que diagnostico antes de reintentar. Primero mido la varianza: corro el mismo commit diez veces y miro la dispersión de cada métrica. Si la dispersión es mayor que mi tolerancia, el gate está mal especificado. Arreglos: fijar el id exacto del modelo juez y la versión de la rúbrica (los jueces actuales de Claude no aceptan temperature, así que esa palanca no existe), muestrear cada pregunta 3 veces y promediar o tomar el voto mayoritario, reportar intervalos de confianza por bootstrap y hacer crecer el dataset para que el CI se angoste. Luego fijo la tolerancia a partir del ruido medido, no de una suposición. También reviso fuentes reales de no determinismo, como empates en retrieval u ordenamientos inestables. Un "retry on failure" a ciegas solo esconde regresiones.

</InterviewQuestion>

<Callout type="interview" title="Di los números">

A los entrevistadores les gustan los gates concretos: "200 ítems golden, subconjunto estratificado de 60 en PRs, 3 muestras cada uno, piso de faithfulness 0.85, tolerancia 0.03, costo por corrida menor a dos dólares gracias al caché del juez". Eso suena a alguien que lo ha operado, no a alguien que lo leyó.
