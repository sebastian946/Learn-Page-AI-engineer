## Company context

Northwind Mortgage is a mid-size US mortgage lender. It has about 600 loan officers, 40 underwriters and a platform team of 12 engineers. In Module 2 you built their internal knowledge assistant, `mortgage-knowledge-assistant`. It answers loan officers' questions over underwriting guidelines, product sheets and internal policies, with citations.

The pilot ran for six weeks with 35 loan officers. Feedback was good. Now leadership wants to roll it out to all 600 officers next quarter.

There is a problem. Nobody can prove the assistant is good. The pilot "evaluation" was a spreadsheet of 50 questions that one engineer re-ran by hand before each release. Prompt changes shipped on gut feeling. One release silently broke citations for a week. Compliance found out from a loan officer, not from a dashboard.

Two other teams want to ship LLM features in the next six months: the collections team (a borrower-facing chatbot for payment plans) and the document operations team (extracting fields from bank statements). The Head of Platform does not want three teams building three different eval stacks.

You are hired as the AI quality engineer. Your job: build a reusable **LLM QA framework**, apply it first to the knowledge assistant, and publish a quality report that compliance can sign off on.

## Business goal

Make LLM quality **measurable, gated and visible**:

1. No prompt, model or retrieval change reaches production without passing an automated eval gate.
2. Every production answer can be traced: question, retrieved chunks, model call, tokens, cost, latency.
3. Compliance gets a versioned, published quality report per release.
4. Other teams can reuse the same toolkit with their own datasets and metrics.

Success in one sentence: the next time a release breaks citations, the PR is blocked before merge, and the report shows exactly which cases regressed.

## Functional requirements

**FR1 — Dataset management.** Load golden datasets from versioned JSONL files. Each case has an `id`, `question`, `reference_answer`, `reference_source_ids`, `tags` (for example `product:fha`, `type:numeric`, `adversarial`) and an optional `expected_behavior` (`answer` or `refuse`). Validate the schema with Pydantic. Print coverage by tag.

**FR2 — Golden dataset for the assistant.** Start from the 50+ pairs you built in Module 2. Extend to about 100 cases. Include at least 15 adversarial or out-of-scope cases (prompt injection inside a question, questions about competitors' rates, requests for borrower PII, questions with no answer in the corpus). Document how each case was created: human-written, mined from pilot logs, or synthetic and reviewed.

**FR3 — Metrics.** Two layers, like a test pyramid:

- Deterministic checks: valid JSON/schema, citation present, cited source ids exist in the retrieved set, numeric values in the answer appear in the cited chunk, refusal on out-of-scope cases, answer length budget.
- Model-graded metrics: faithfulness, answer relevance, context precision and recall (Ragas or DeepEval, or your own judge prompts).

**FR4 — Calibrated judge.** Any custom LLM judge must ship with a calibration report against at least 40 human-labeled examples: agreement rate, Cohen's kappa, confusion matrix, and known biases tested (position bias for pairwise, verbosity bias). The judge prompt and model id are versioned.

**FR5 — Runner.** Run the target app over the dataset with bounded concurrency, retries and a response cache keyed by prompt version, model id and input hash. Support `--sample N` for fast PR runs and a full run for nightly or release.

**FR6 — Gate.** Compare a run against a stored baseline. Fail on: absolute thresholds (for example faithfulness below 0.85), relative regressions beyond a tolerance (for example a drop of more than 0.03 on any metric), or any failure in a `critical` tag. Output a machine-readable result and a markdown summary.

**FR7 — CLI.** `llmqa run`, `llmqa gate`, `llmqa report`, with a single `llmqa.toml` config per project.

**FR8 — CI integration.** A reusable GitHub Actions workflow (`on: workflow_call`) that other repos call with a few inputs. It posts the markdown summary as a PR comment and uploads the run as an artifact.

**FR9 — Tracing.** Instrument the assistant with OpenTelemetry using the GenAI semantic conventions: spans for retrieval, re-ranking, LLM call and any tool call, with token usage and model attributes. Export to Langfuse (or LangSmith) and to the SRE team's OTLP collector. Eval runs link each case to its trace id.

**FR10 — Red-team suite.** A tagged set of attacks (direct and indirect prompt injection via a poisoned document, PII extraction, policy fabrication, jailbreak attempts) run as a separate job, with pass/fail per OWASP LLM Top 10 category.

**FR11 — Quality report.** A static report (HTML or markdown) generated per run: summary scores vs baseline, per-tag breakdown, worst 10 cases with trace links, judge calibration, red-team results, cost and latency. Published to GitHub Pages, one page per release, with history.

## Acceptance criteria

- `llmqa run --config examples/mortgage-knowledge-assistant/llmqa.toml --sample 30` finishes under 10 minutes and logs total cost.
- Introducing a deliberate regression (for example removing the "cite your sources" instruction from the prompt) makes the CI gate fail with a clear message naming the metric, the delta and the top failing cases.
- Reverting the regression makes the gate pass.
- The golden dataset has at least 100 cases, at least 15 adversarial, and coverage by tag is printed in the report.
- The judge calibration report shows kappa at least 0.6, or documents why not and what was changed.
- Every eval case in the report links to a trace showing retrieval, LLM spans and token usage.
- Traces contain no unredacted PII from a seeded test case containing a fake SSN and email.
- The red-team job runs nightly and its results appear in the report.
- A second, toy project (for example a 10-case "collections FAQ" bot) adopts the toolkit using only the README and the reusable workflow.
- The quality report is live on GitHub Pages.

Design notes:

- The adapter is the only project-specific code. It maps a dataset case to a call into the app and returns `answer`, `citations`, `contexts`, `trace_id`, `usage`. That is what makes the toolkit reusable.
- Deterministic metrics run first and are free. Model-graded metrics only run on cases that pass schema checks.
- The cache key includes prompt version and model id, so a prompt change always invalidates its own cases but unchanged code paths stay cheap.
- Redaction happens in a span processor before export, not in the exporter config, so every backend gets clean data.

## How to present this in an interview

This capstone is your strongest differentiator. Most AI engineering candidates can build a RAG demo. Few can prove it works and keep it working. You can, because you have done this for years with deterministic software.

**The 60-second pitch.** "A mortgage lender's knowledge assistant was moving from pilot to 600 users with no way to prove quality. I built a reusable LLM QA framework: a versioned golden dataset of about 100 cases, a two-layer metric stack with deterministic checks and calibrated LLM judges, a CI gate that blocks PRs on faithfulness regressions, OpenTelemetry tracing with PII redaction, a nightly red-team suite, and a published quality report. A deliberate citation regression gets blocked in under 10 minutes for about two dollars per run." Replace the numbers with your real ones.

**Map it to your QA background out loud.** Interviewers like the translation:

- Test pyramid becomes the eval pyramid: cheap deterministic checks, then model-graded metrics, then human review.
- Flaky tests become non-determinism: you pinned model ids and rubric versions, cached responses, sampled repeatedly and used tolerances instead of exact matches.
- Regression suite becomes the golden dataset, with versioning and coverage by tag.
- Contract tests become output schemas and citation checks.
- Test reports become the published quality report.

**Expect these follow-ups and prepare answers:**

- "How do you know your judge is right?" Talk about the labeled set, kappa, the confusion matrix, and the bias you found and fixed.
- "How do you avoid a flaky gate?" Talk about tolerance bands, repeated sampling on borderline cases, critical tags and the cache.
- "What does it cost?" Give the cost per PR run, per nightly run and cost per 1k requests for the app.
- "What did you find?" Have one real story: a case the gate caught, a bias in the judge, or an injection that worked before you added a guardrail.
- "How would another team adopt it?" Show the adapter interface and the reusable workflow call. Mention the toy second project.

**Show, don't tell.** Open the GitHub Pages report. Then show the PR where the gate failed, the comment with deltas, and click through to the Langfuse trace of the worst case. That three-click story beats any slide.
