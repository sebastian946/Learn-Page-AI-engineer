## Goal

Before you let a judge block pull requests (exercise 06), you prove it agrees with humans. In this exercise you build a small calibration workflow in your `llm-eval-harness` repo:

1. A human-labeled set of about 30 RAG outputs from your Module 2 mortgage assistant.
2. A faithfulness judge with a versioned rubric.
3. A script that runs the judge, computes agreement, Cohen's kappa and a confusion matrix, and lists every disagreement.
4. At least one rubric iteration, measured on a held-out split, with the results written to a calibration report.

This is the QA equivalent of validating a new test oracle before trusting it in the pipeline.

## Context

You will create the labeled set yourself. Run 30 golden questions through `mortgage-knowledge-assistant` (or reuse saved outputs from Module 2) and store, per case: the question, the retrieved contexts, the answer. Then label each one **as a domain expert would**: `faithful` or `unfaithful`, with a one-line note. To get enough failures, deliberately produce some bad outputs: shrink `top_k` to 1, remove the "answer only from context" instruction, or edit a few answers by hand to change a number. Aim for roughly 30–40% unfaithful cases. A set with 2 failures cannot measure anything.

Label **before** you run the judge, so its verdicts do not anchor you. If a friend or colleague can label 10 cases independently, compute human-human kappa too. That is your ceiling.

Use this row format in `calibration/human_labels.jsonl`:

```json
{"id": "cal-007", "question": "Is PMI required on a conventional loan with 15% down?", "contexts": ["Conventional loans with less than 20% down require private mortgage insurance (PMI)..."], "answer": "Yes. With 15% down, PMI is required until you reach 20% equity.", "human_label": "faithful", "labeler": "jd", "note": "Matches policy 4.2"}
```

- [ ] Judge calls are cached on disk keyed by (model, rubric hash, case id), so reruns are free

- [ ] `calibration/REPORT.md` records judge model, rubric version, kappa, false-faithful rate, date and a go/no-go decision for using the judge as a CI gate (target: kappa at least 0.6 and false-faithful rate at most 10%)

<Hints>
  <Hint>Get the data right first. Twenty minutes spent creating realistic unfaithful answers (a wrong percentage, an invented fee, a claim the context never makes) is worth more than any rubric tweak. Keep the failure types varied, or your kappa only measures one kind of error.</Hint>
  <Hint>Use `asyncio.Semaphore(5)` around the judge call and `asyncio.gather` over the cases. Write the cache file only after `Verdict.model_validate_json` succeeds, so a malformed response is retried next run instead of cached.</Hint>
  <Hint>For the false-faithful rate, the confusion matrix with `labels=["faithful", "unfaithful"]` gives rows as human and columns as judge. The dangerous cell is row "unfaithful", column "faithful": `cm[1][0] / cm[1].sum()`.</Hint>
  <Hint>Typical v1 failures: the judge forgives "reasonable" claims not in the context, or punishes correct refusals. Typical v2 fixes: state that unsupported-but-plausible claims are unfaithful, state that "the documents do not cover this" is faithful, ask for a claim-by-claim list before the verdict, and add one short worked example that is not in your held-out split.</Hint>
